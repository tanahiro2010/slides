# draft-creater

`draft.md` は**発表の中身を構造にしたもの**。
記事の設計メモでも、調べたことの要約でもない。

既存ドラフトは 2 系統ある。**真似るのは形式だけ。** 中身も口調も引きずらない。

## まず判断：どちらの形式か

| | 検証系 | LT 系 |
| --- | --- | --- |
| 置き場 | `slides/slides/` | `slides/speakerdeck/` |
| 例 | DPoP 検証、Hono v5、Step-up Authorization | WebMCP 登壇、Hono を使え、ドッグフーディング |
| 本体 | 採番した `##` 節 | `## 記事・スライド共通ドラフト` の下の箇条書き |
| 規模 | 400〜760 行 | 100〜300 行 |
| 向く題材 | 測った / 検証した / 仕様を突き合わせた | 体験した / 紹介する / 主張する |

迷ったら**置き場で決める。** `slides/slides/` に作るなら検証系。

## 一番やりがちな失敗

### 1. 編集方針を書く

```markdown
- で、どこまで守ってくれるのか
  - 記事の山場
  - 長くしない
  - 軸にぶら下がらないものは落とす
```

これでは読んだ人がスライドを作れない。**そのスライドに載る中身**を書く。

```markdown
- で、どこまで守ってくれるのか
  - ドキュメントは「出力が始まる前なら」としか書いていない
  - 切る位置だけ変えて測った
    - 何も出さずに切断 → 切り替わる
    - ツール名だけ届いた → 切り替わる
    - 本文が 1 文字出た → 切り替わらない
```

### 2. 既存ドラフトの口調を写す

既存ドラフトには書き手固有の言い回しが入っている。
**それは真似る対象ではない。** 真似るのは次の 3 つだけ。

- 節の構成
- 箇条書きのネストの深さと粒度
- 1 節あたりの分量

題材に合う書き方で書く。無理に砕けさせない。

## 置き場所

```
slides/<group>/<名前>/
├── draft.md     ← これを作る
├── summary.md   summary-creater が draft を文章にしつつ裏取りする
├── article.md   article-creater が summary を読んで作る
└── slide.md     slide-creater が draft から直接作る（別系統）
```

## 検証系の形

`slides/slides/` に置くもの。雛形は `references/template-verify.md`。

```markdown
# <タイトル>

<状態メモ。検証がどこまで終わったか、公開してよいか、開示の経緯>

## 一次ソース
## 表現のルール（slide でも守る）
## タイトルまわり
## つかみ
## この発表のスタンス

---

## 1. <節タイトル> ―― <補足>
## 2. ...
## 7. <節タイトト>（🔥 山場その1）

## 検証前チェックリスト
## メモ（サンプルコード・資料）
```

### 効く節

**`## 一次ソース`** は URL だけでなく**更新日を書く**。
どちらを先に疑うかの材料になる。

```markdown
- DPoP Adoption Guide（更新 2026-07-31）: https://...
- OAuth 2.0 for Web Server Applications（更新 2026-10-16）: https://...
- RFC 9449（DPoP, 2023-09）: https://...
```

**`## 表現のルール`** が一番あとで効く。言い換えと禁止事項を先に決める。

```markdown
- ❌「DPoPが新登場」→ ⭕「RFC 9449で2023年に標準化済み。Googleが対応した」
- 「暗号化」と「鍵にバインド」を書き分ける
- リプレイの件は煽らない。「ドキュメントと実装の食い違い」として扱う
- ログ・記事に秘密鍵や完全な proof を出さない
```

**`## この発表のスタンス`** は、やらないことを書く。

```markdown
- 公式ドキュメントの翻訳記事にはしない
- 「ドキュメントにこう書いてある」ではなく「実際にこうなった」を出す
- 検証できなかったものは「できなかった」と書く
```

### 節の中身

1 節 **15〜45 行**。箇条書き・表・コードブロックを混ぜる。

```markdown
## 8. ES256は本当に重いのか

- blog の主張：高QPS APIで毎回DPoP検証するとコストが massive
- ✅ 実測（Node v24.22.0 / Apple M4 / N=20,000、📋 メモ⑮）

  | | µs/op | ops/s |
  | --- | ---: | ---: |
  | sign | 26.2 | 38,227 |
  | verify | 50.5 | 19,787 |

  - 検証は署名の約2倍、1コア毎秒2万回
- 📌 71B。§7 のサンプルは70B。DER長は 69〜72 で揺れる
```

- 表は**実測値の比較**に使う。推測を並べない
- 長いコードは本文に置かず `## メモ` に逃がし、`📋 メモ⑮` で参照する
- 記号は意味を持たせる。`🔥` 山場 / `✅` 実測済み / `📌` 補足 / `📋` メモ参照 / `§7` 節参照

## LT 系の形

`slides/speakerdeck/` に置くもの。雛形は `references/template-lt.md`。

```markdown
# <タイトル>

## 概要
## LTスライドを作るに当たって
## 記事を書くに当たって

## 記事・スライド共通ドラフト
- タイトル
- 自己紹介（要るときだけ）
- <スライド>
  - <中身>
- 締め
```

前 3 節はほぼ定型。雛形から写す。
`## 記事・スライド共通ドラフト` が本体で、**トップレベルの `-` が 1 枚**。

既存ドラフトの注記がこれ。

> 一セクションに一つ書いてますが、別にそれで一ページと言うわけでもなく分量によって分割推奨

分量が多ければ `slide-creater` が割る。書く側は意味のまとまりで切る。

## どちらにも共通すること

### ネストは 2〜4 段

浅いと中身が無い。深いと読めない。
**3 段目あたりに具体物**（数値・URL・ファイルパス・引用）が来る。

```markdown
- 初期登録とセッション期間の違い      <- 1 段目
  - MCP は Agent 起動時に登録される    <- 2 段目
    - exit するまで使える             <- 3 段目
```

### 具体物を書く

| 書く | 書かない |
| --- | --- |
| `画像：img/tanaka.png` | 「画像を入れる」 |
| `connpass: https://...` | 「イベントページを参照」 |
| `328ms、32 パート` | 「速かった」 |
| 相手の発言を引用符で | 「指摘をもらった」 |

**あとで探し直す羽目になるものは、全部ここに書く。**

### 数値は測ってから書く

「速かった」と書いた瞬間、測り直しが確定する。
検証系なら `claims.md` / `sandbox/` から写す。

### 自己紹介は要るときだけ

イベント登壇なら入れる。記事中心なら省く。
`slides/speakerdeck/` の 11 本中 2 本にしかない。

### 締めを置く

LT 系は必ず置く。検証系は「まとめ」節が代わりになる。

## よくある失敗

- **編集方針を書く。** 「山場」「長くしない」は draft の中身ではない
- **既存ドラフトの口調を写す。** 形式だけ借りる
- **要約してしまう。** 調べた内容の要約ではなく、発表の中身を書く
- **形式を取り違える。** 検証ネタを LT 系の箇条書きだけで書くと、一次ソースと表現のルールが落ちる
- **数値を後回しにする**
- **表に推測を並べる。** 表は実測値の比較に使う
- **長いコードを本文に置く。** `## メモ` に逃がす
