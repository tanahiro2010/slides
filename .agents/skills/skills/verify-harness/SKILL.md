# verify-harness

> 全体の流れは `verify-pipeline`。このスキルはその **フェーズ 4**。
> 実機不要で取れるもの（フェーズ 3）を先に潰してから来ると速い。

`claims.md` の主張を、**実際に叩いて確かめるコード**を書く。出力は `<デッキ>/sandbox/`。

このスキルの中身は、ほぼ全部が**実際にやらかして学んだこと**でできている。
先に読めば、同じ 1 時間を 2 回払わずに済む。

## 鉄則

> **ログに残らない観測は、結論に使わない。**

一度やらかした。「使用済み nonce を再送 → 200」という結果を記録したが、
**内側で先に投げた 1 回目のステータスを出力していなかった**。
1 回目が失敗していたなら nonce は消費されておらず、2 回目が通るのは当たり前。
つまりあの観測からは何も言えなかった。判定を取り下げて、測り直しになった。

**送ったものと返ったものを、全部ログに出してから結論を書く。**

---

## 1. 記録は最初から仕込む

**「あとで JSON に残しておけばよかった」は必ず来る。** 1 行目から仕込む。

整形された出力は読みやすいが、**報告にも再現にも使えない**。要るのは生の往復。

1 リクエスト = 1 行の JSONL で、これを全部残す:

```json
{
  "seq": 1,
  "timestamp": "...",
  "request":  { "method": "POST", "url": "...", "headers": {...}, "form": {...} },
  "response": { "status": 200, "headers": {...}, "body": {...} },
  "durationMs": 144
}
```

- **レスポンスヘッダーを全部残す**（あとで効いてくるのはだいたいここ）
- 署名付きトークンを送っているなら、**デコードした中身も添える**（読む側が base64 を開かずに済む）
- 通信層に 1 つフックを置き、全送信をそこに通す。**フックを通らない送信を作らない**

実装の型は `references/recorder.md`。

## 2. 対照をコードに埋める

**「X できる」と「X が見られていない」は別の主張。** 区別する対照が無いと結論が出ない。

実例。「同じ nonce を 6 回使って全部 200」だけでは、
**nonce が再利用できる**のか**そもそも検証されていない**のか分からない。
対照を足して決着した:

| 送った nonce | 結果 | |
| --- | ---: | --- |
| でたらめな乱数 | 400 | ← これが無いと何も言えない |
| 1 文字だけ変えた | 400 | |
| 正しい値を 6 回 | 全部 200 | |

でたらめが弾かれる＝**検証はされている**。その上で再利用できる、と言える。

対照は**同じスクリプトの中に並べる**。別々に走らせると条件が揃わない。

## 3. 同一性は指紋で示す

「同じものを送った」を主張するなら、**ログで証明できる形**にする。

- 送信バイト列の **SHA-256 を毎行に出す**。ハッシュが一致＝同じものを送った証拠
- 伏せたい秘密は、消すのではなく**不可逆な指紋に置き換える**

```json
"refresh_token": { "_redacted_len": 103, "_sha256_16": "7ec99861890b84a9" }
```

これで秘密を出さずに、**同一性と差異の両方**が示せる。実際にこれが効いた:

- `refresh_token` の指紋が全記録で**同じ** → 同じトークンに対する再送だと証明できる
- `access_token` の指紋が毎回**違う** → キャッシュや no-op ではなく本当に再発行されている証明

単なる `<redacted>` だと、この 2 つがどちらも言えない。

## 4. 長い測定は中断・再開できるようにする

時間が効く検証（有効期限、TTL、レート制限）は、**途中で止まる前提**で書く。

- 測定対象と経過を**1 回ごとにファイルへ保存**する
- 再開時は、保存した開始時刻から経過を計算して**遅れた分はすぐ投げる**
- 予定の分数とは別に、**実際の経過秒を記録**する（スリープや再開でずれる）
- 落ちても、そこまでの結果を書き出す

1 時間かかる測定を、プロセスを一度止めただけで最初からやり直すのは痛い。
**実際に「止めても大丈夫ですか？」と聞かれてから直した。** 最初から入れておく。

## 5. 検証順序の罠

**片方の検証が先に走ると、もう片方のバグが隠れる。**

実例。Google は grant を proof より先に検証していた。
壊した proof を 8 通り投げても、Refresh Token が無効なら**全部 `invalid_grant`**。
proof のバグは一切表に出てこない。

ここから出る手順:

> **まず検証したい機能を外した状態で通す。それから機能を足す。**

DPoP なしで Refresh が通ることを確認してから DPoP を足す。
これをやらないと、どちらが壊れているのか永久に切り分けられない。

ついでに、**検証順そのものが成果になる**（`claims.md` の「沈黙」項目）。

## 6. 境界は二分探索で、1 秒まで詰める

閾値（タイムアウト、許容スキュー、上限値）は、段階プローブで終わらせない。

- 「600 秒は通る / 3600 秒はダメ」では**実装定数が見えない**
- 二分探索で 1 秒まで詰めたら **ちょうど 3600 秒**と **ちょうど 10 秒**だった。
  丸い数字が出た時点で、実装定数だと分かる
- **前回の答えを知らない範囲から探索し直す**と、独立した再現になる

## 7. 秘密情報

- 認証情報は `.env`。**`.gitignore` を書いてから** `.env` を作る
- 生ログ・鍵・トークンの保存先（`data/` など）も最初から除外する
- 画面と整形ログには、トークンの**中身を出さず長さだけ**出す
- 公開リポジトリなら、**scratch ファイルも除外**しておく（`test.json` のような置き場が後で生える）

> ⚠️ 公開リポジトリで検証するなら、**コミットメッセージにも書かない**。
> 詳しくは `verify-judge` の開示パート。

## ディレクトリの型

```
sandbox/
├── .env.example      プレースホルダだけ
├── .gitignore        .env / data/ / 生ログ / scratch
├── src/
│   ├── config.ts     設定と固定値
│   ├── <core>.ts     検証対象の中核（ここが記事のコードになる）
│   ├── client.ts     通信層。例外を投げず status/headers/body をそのまま返す
│   ├── evidence.ts   記録フック（references/recorder.md）
│   └── <scenario>.ts 検証シナリオ。claims.md の # と対応させる
└── data/             生ログと状態（gitignore）
```

**通信層は例外を投げない。** 400 も立派な観測結果なので、握りつぶさず返す。

## よくある失敗

- **整形出力だけ残す** — 報告にも再現にも使えない。生の往復を残す
- **内側の呼び出しを記録しない** — そこから出した結論は取り下げることになる
- **対照を置かない** — 「できる」と「見ていない」が区別できない
- **`<redacted>` で潰す** — 同一性が示せなくなる。指紋にする
- **長い測定を使い捨てで書く** — 止めた瞬間に 1 時間が消える
- **検証したい機能を最初から入れる** — 別の層のエラーに隠れて切り分けられない
- **段階プローブで満足する** — 二分探索で丸い数字まで詰めると、実装定数が見える
- **`.env` を作ってから `.gitignore` を書く** — 順番が逆
