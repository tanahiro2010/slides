# verify-judge

> 全体の流れは `verify-pipeline`。このスキルはその **フェーズ 6〜7**。

測った後がいちばん間違えやすい。**データが支えている範囲を超えて書かない**ための手順。

実際にこのフェーズで 2 回やらかした。1 回は記録していない観測から結論を書き、
1 回は「約 1 時間リプレイできる」と**測っていない条件込みで**主張した。
どちらも取り下げて測り直した。

## Workflow

1. **観測と解釈を分けて書く**（下記）
2. **対照が揃っているか確認する。** 無ければ結論を保留して測り直す
3. **主張を最小に狭める**（下記）
4. **独立に再現する**（下記）
5. 重大そうなら **深刻度を正直に切る**（下記）
6. 報告するか決める → `references/disclosure.md`
7. 公開範囲を決める。**開示が終わるまで公開しない**

---

## 観測と解釈を分ける

`claims.md` に書き戻すとき、この 2 つを別の行にする。

| | 例 |
| --- | --- |
| **観測** | 同じ nonce を 6 回送って、6 回とも 200 が返った |
| **解釈** | nonce は検証されるが消費されない |

観測は動かない。解釈は、対照が増えると変わる。

実際、対照（でたらめな nonce → 400）を足す前は
「**再利用できる**」のか「**そもそも見ていない**」のか決められなかった。
**対照が無い観測から解釈を書かない。**

## 主張を最小に狭める

**条件が複数あるなら、全部測ったか確認する。**

やらかした実例。「捕捉した proof は約 1 時間リプレイできる」と書いた。
だが成立条件は 2 つあった。

1. `iat` が 3600 秒以内 ← 測定済み
2. proof に入っている nonce がまだ有効 ← **未測定**

検証では「古い `iat` + その場で取った新しい nonce」を送っていた。
現実に盗まれた proof は**両方が一緒に古くなる**ので、条件が違う。
本当の窓は `min(3600秒, nonce の寿命)` で、後者を測っていなかった。

→ 判定を「要追試」に下げ、1 時間かけて測り直した。結果は iat 側が上限だったので
最終的に主張は通ったが、**測る前に書いていたら嘘だった。**

チェック:

- 主張に `かつ` が隠れていないか。隠れていたら各項を測ったか
- 実験の条件は、主張している**現実のシナリオと同じ**か
- 「最大 N」と言うなら、N を**直接**測ったか（推論で出していないか）

## 独立に再現する

重い主張を出す前に、**ゼロからやり直す。**

- 状態を全部リセットして、**新しい認証情報・新しい鍵**から
- 前回の答えを**知らない範囲**から二分探索し直す
- 対照を足した版で測る
- **全送信をログに通す**（`verify-harness` の鉄則）

今回これをやったら、全項目が再現し、`iat` の境界は 1 秒単位で 2 回とも同じ値になった。
**別経路で同じ数字が出たら、実装定数だと言える。**

再現で値が食い違ったら、**新しい方が正しいのではなく、対照が足りなかった方が間違い**。

## 深刻度を正直に切る

セキュリティ上の発見に見えたら、**盛らずに切る。** 盛った報告は通らないし、信用も減る。

問うこと:

> **その発見は、攻撃者の能力を増やしているか？**

実例。proof を 1 時間再利用できる、は派手に見えた。だが:

- proof を観測できる立場なら、同じリクエストの `refresh_token` も `client_secret` も取れる
- しかも proof 単体では `invalid_grant` で弾かれる（別の検証で判明）
- → **再利用の窓があっても、捕捉で得た能力を増やしていない**

だから CVSS は Low（`AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N` ≈ 3.7）。
実態は informational に近い、と自分で書いた。

**この正直さが報告の芯になる。** 実際ベンダーの回答も同じ理由だった。

| 切り分け | それは何か |
| --- | --- |
| 攻撃能力が増える | セキュリティバグ。報告する |
| 増えないが、RFC の hardening 条件を外している | 設計の弱み + ドキュメント問題 |
| 挙動は妥当だが、記述が違う | **ドキュメントのバグ**。それでも書く価値はある |

## 相手の回答も結論の一部

報告の返答は、finding の**性質を確定させる材料**になる。

実例。Won't Fix（Infeasible）が返ってきた。理由は「アカウント乗っ取り・権限昇格・
認証バイパスが無く、影響が限定的」。

これで「**セキュリティバグではなく、ドキュメントと実装の食い違いである**」と
ベンダー自身が位置づけたことになる。記事の主張がそれで裏付けられた。

**却下されたことを隠さない。** 報告して却下された、という結末まで書くと、
主張の強さがむしろ上がる。

## 公開してよくなるまで

順番を守る。

1. 発見を**公開素材から外す**（`references/disclosure.md` の手順）
2. 報告する
3. 相手の回答を待つ
4. 回答が出てから公開する

> ⚠️ **コミットメッセージも漏れる。**
> ファイルを消しても、メッセージ本文に発見内容が残る。実際に
> 「proof のリプレイが成立することを記録」のようなメッセージが
> 公開リポジトリに残っていた。履歴を書き換えるときは**メッセージも対象**。

公開リポジトリで作業しているなら、消し方は `references/disclosure.md`。

## 記事に書くときの線

- **観測した事実**は断定する
- **解釈**は解釈として書く
- 影響が限定的なら、**限定的だと書く**。煽らない
- 却下されたなら、その理由ごと書く
- 「検証の裏側」（ログが崩れた、取得できなかった）は書かない。
  これは `references.md` に残すもの（`references-creater`）

## よくある失敗

- **対照の無い観測から結論を出す** — 取り下げることになる
- **条件を全部測らずに「最大 N」と言う** — 隠れた `かつ` を数える
- **再現せずに重い主張を出す** — ゼロからやり直すと矛盾が出ることがある
- **深刻度を盛る** — 通らないし、次の報告の信用も減る
- **却下されたことを書かない** — 却下の理由こそが性質の確定になる
- **ファイルだけ消して公開する** — コミットメッセージに残る
- **報告前に記事を出す** — 順番が逆
