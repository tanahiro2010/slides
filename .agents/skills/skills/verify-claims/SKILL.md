# verify-claims

> 全体の流れ（調査→主張→コード→実機→判定→開示→執筆）は `verify-pipeline`。
> このスキルはその **フェーズ 2**。

仕様書は**検証対象**であって、正解ではない。

実際に Google OAuth の DPoP 対応を 4 方向（公式ドキュメント / RFC / 自分の計測 / 実機）から
突き合わせたら、**詰まった箇所は 1 つ残らずドキュメントとの差分**だった。
公式サンプルの署名は壊れていたし、公式ドキュメント同士が逆のことを書いていた。

このスキルは、その差分を**見つける前に数え上げる**ためのもの。
出力は `<デッキ>/claims.md`。雛形は `references/template.md`。

## 置き場所

```
slides/<group>/<名前>/
├── claims.md       ← これを作る（検証計画）
├── references.md   ソース集め（references-creater）
├── sandbox/        検証コード（verify-harness）
└── draft.md
```

`references-creater` との違い。あちらは**ソースを集める**（何が書いてあるか）。
こちらは**集めた記述を真偽判定できる文に割る**（書いてあることは本当か）。
先に references.md を作ってからこちらに来るのが自然。

## Workflow

1. **一次資料を並べる。** 仕様書・RFC・ベンダードキュメント・公式サンプル・SDK。
   **更新日を必ず記録する**（下の「新しい方が正しいとは限らない」）。
2. **断定文を抜く。** 「〜する」「〜を返す」「〜は MUST」。
3. **1 文を複数の主張に割る**（下記）。
4. 各主張に **確かめ方**と**対照**を書く。
5. **矛盾と沈黙を拾う**（下記 2 つ）。
6. `claims.md` に表で書き出す。これが `verify-harness` の入力になる。

---

## 1 文を複数の主張に割る

ドキュメントの 1 文には、たいてい複数の検証可能な主張が入っている。
**文のまま扱うと、どれが外れたのか分からなくなる。**

実例。web-server doc のこの 1 文:

> If the DPoP proof has mismatching `htm` or `htu` claims, an expired `iat`,
> a re-used `jti`, or an invalid signature, Google returns an `invalid_dpop_proof` error code.

これは **5 つの主張**。割って個別に試したら、こうなった。

| doc の主張 | 実測 | |
| --- | --- | --- |
| `htu` 不一致 → `invalid_dpop_proof` | `invalid_request` | ❌ |
| `htm` 不一致 → `invalid_dpop_proof` | `invalid_request` | ❌ |
| `iat` 期限切れ → `invalid_dpop_proof` | `invalid_dpop_proof` | ✅ |
| `jti` 再利用 → `invalid_dpop_proof` | **エラーにならない** | ❌ |
| 署名不正 → `invalid_dpop_proof` | `invalid_dpop_proof` | ✅ |

**5 つのうち 3 つが違った。** 文のまま「だいたい合ってる」で済ませたら、
この 3 つは出てこない。

## 矛盾を先に探す

**同じベンダーの別のページが、逆のことを書いていることがある。**
これは実機を叩く前に、読むだけで見つかる。一番安く取れる成果。

探し方:

- 同じ概念が**複数のページ**に出てくるなら、両方読んで突き合わせる
- **更新日の違うページ**を特に疑う
- 入門ガイドとリファレンスは、よくズレている

実例。Nonce を持ち越せるかで、公式ドキュメント同士が割れていた。

| | 言っていること |
| --- | --- |
| Adoption Guide（07-31） | workflow をまたぐと**無条件に 400** |
| web-server doc（10-16） | その nonce で**余分な往復を避けられる** |

実測したら 400。**古い方が正しかった。**

### 新しい方が正しいとは限らない

上の例では、**新しい web-server doc の方が間違っていた**。
「最終更新が新しいページを信じる」は通用しない。更新日は**どちらを先に疑うか**の
材料であって、正解の根拠ではない。

## 沈黙も主張にする

**書いていないことは、検証項目として一番価値が高い。** 誰も答えを持っていないから。

実例:

| 書かれていなかったこと | 実測した値 |
| --- | --- |
| `iat` の許容範囲 | 過去ちょうど 3600 秒 / 未来ちょうど 10 秒 |
| grant と proof の検証順 | grant が先（proof のバグが `invalid_grant` に隠れる） |
| 成功レスポンスの謎フィールド | 値は別ヘッダーと同一 |

探し方:

- エラーの**条件は書いてあるが、閾値が書いていない**（タイムアウト、許容スキュー、retry 回数）
- **順序が書いていない**（どっちを先に検証するか、どっちが優先か）
- サンプルに**出てくるのに本文で説明されていない**フィールド
- 機械可読な宣言（discovery / metadata）に**出ていない**対応状況

## 公式サンプルも検証対象

**コピーして動かす前に、サンプル自体を検証する。**

実例。公式ガイドの proof サンプル 2 つのうち、片方は**署名検証を通らなかった**。
JWS が要求する 64 バイトの raw 形式ではなく、ASN.1 DER のまま貼られていた。
しかもそれは、同じベンダーが別ページで「変換しろ」と書いている当の間違い。

もう 1 つのサンプルは **RFC の例文の丸写し**で、エンドポイントすら自社のものではなかった。

サンプルに対して最低限やること:

- 署名・ハッシュがあるなら**検証する**
- 埋め込まれた値を**デコードして中身を見る**（`iat` の日付、URL、ID）
- 本文に書いてあるルールと、サンプルが**一致しているか**

## 2 つの仕様を比べるとき

「A と B は何が違うのか」という問いは、**差分の軸を先に決めない**と散らかる。

軸の候補:

| 軸 | 問い |
| --- | --- |
| 主体 | 誰が要求するのか |
| きっかけ | 何をトリガに発動するのか |
| 責務 | プロトコル上、どちらが何を持つのか |
| 失敗時 | 何を返すのか。エラーコードは |
| 前提 | 片方にあって、もう片方に無い要件は |

**体験が似ているものほど、プロトコル上の責務で割る。** 画面の見た目で比べない。

## claims.md の判定記号

`references-creater` と揃える。

| | 意味 |
| --- | --- |
| ⬜ | 未検証。これから `verify-harness` で確かめる |
| ✅ | 書いてある通りだった |
| ❌ | **書いてあることと違った** |
| ⚠️ | 対照が足りず、まだ結論を出せない |
| 📭 | 書かれていなかった（実測するしかない） |

## よくある失敗

- **文のまま主張として扱う** — 5 つの主張が入った 1 文を ✅/❌ で判定しない
- **矛盾を探さずに実機へ行く** — 読むだけで見つかるものを、測ってから気づく
- **「書いていない」を検証項目にしない** — ここが一番おいしいのに落とす
- **公式サンプルを信じてコピーする** — 動かない上に、原因が自分のコードに見える
- **更新日が新しい方を正解にする** — 実例では新しい方が間違っていた
- **確かめ方を書かずに主張だけ並べる** — `verify-harness` が受け取れない
- **対照を設計しない** — 「再利用できる」と「そもそも見ていない」は別の主張。
  区別するには**でたらめな値を送る対照**が要る（`verify-harness` 参照）
