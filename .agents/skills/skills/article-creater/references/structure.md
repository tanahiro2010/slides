# 記事の骨格

公開中の記事はすべてこの形をしている。崩さない。

```markdown
---
published: false
---

# 本タイトル（長くてよい。検索に効く）

> エピグラフ。記事を象徴する一文を引用で置く

## この記事の結論

[2〜3文。何をして、何が分かったのか]

- 要点1
- 要点2
- 要点3

[数字や構成があるなら表で出す]

| 項目 | 結果 |
| --- | ---: |
| … | … |

ソースコードはこちらです: https://github.com/…

そして、この記事で一番伝えたいことを先に書いておきます。

**[一文で言い切る]** [その理由を2〜4文]

> この記事は〇〇の登壇内容に、発表では話しきれなかった〜を足したものです。
> 対象は〜。

---

## 1. 〜
## 2. 〜
…
## N. まとめ

### 参考

- [リンク](URL) — 何が書いてあるか一言
```

## 各パーツの役割

### エピグラフ

タイトル直後に引用 1 行。記事の主張か、読者の素朴な疑問を置く。

- `> Infrastructure as Code。つまり Code。なら何でもできますよね？`
- `> AI = 演技、TypeScript = 世界。……のはずでした。`
- `> Serverless の方が楽なのに、どうしてわざわざ自分でサーバーを管理するの？`

### この記事の結論

**結論を最後まで引っ張らない。** 読者は目次ではなく結論で読むかを決める。

含めるもの:

1. 何をして何が分かったか（2〜3文、太字で要点を1つ）
2. 箇条書き 3 点
3. 数字・構成・比較があれば表
4. ソースコードや資料の URL
5. `**[一番伝えたいこと]**` — 技術的な学びを一文で言い切る
6. 引用ブロックで「この記事は〜の登壇内容を〜」と出自と対象読者

6 を引用ブロックに入れるのは、本文の流れから外れたメタ情報だから。
ここで初めて「どのイベントで話したか」を書く。冒頭の自己紹介は要らない。

### 本文（採番した h2）

`## 1. 発端` のように連番を振る。読者が「今どこか」を見失わないため。

- 長い記事（20,000字超）は冒頭に `## 目次` を置いてよい。
  **置くなら本文の見出しと必ず一致させる。** 手で書くとズレる。
- ハマりどころは `### ハマりポイント①：〜` の形で独立させる。
- 計測した数字は `### 計測：〜` と `### 考察：なぜそうなるのか` に分ける。
  数字だけ出して考察しないのは手抜き。

### 参考

一次資料があるなら `### 参考` で締める。リンクの後ろに「何が書いてあるか」を
一言添える。URL だけ並べない。

```markdown
- [Terraform: Backend Configuration](https://…) — State の置き場所と `init` の移行挙動
```

**実在するものだけ書く。** 読んでいない資料を参考に挙げない。

## 長さの目安

公開記事は 3,000〜19,000 字（タグを除いた文字数）。
LT 1 本の書き起こしなら 5,000〜10,000 字あたりに落ち着く。

短くても構わない。薄いまま長くする方が悪い。
