# AI が書いた感じを消す

この記事群は AI に下書きさせることが多い。そのまま出すと読者に「AI が書いたな」と
分かる。原因は 3 つに絞れる。

1. 文の長さと構造が一定で、リズムがない
2. 具体的な体験がなく、一般論の羅列になる
3. 評価を避けて、常に両論併記で逃げる

出典: [AIに書かせた技術記事を人間っぽくする5つの編集テクニック](https://qiita.com/kawabe0201/items/34b2fdbd4f2eff1872e0)

**この 3 つのうち 1 と 3 は、書き上がった後に機械的に測れる。** 先に測る。

---

## まず測る

書き上がったら、本文に対してこれを走らせる。目で読む前に数字を見る。

```sh
python3 - <<'EOF'
import re, statistics, collections
s = open('article.md', encoding='utf-8').read()
s = re.sub(r'^---\n.*?\n---\n', '', s, flags=re.S)   # frontmatter
s = re.sub(r'```.*?```', '', s, flags=re.S)          # コードブロック
body = [l.strip() for l in s.split('\n')
        if l.strip() and not l.strip().startswith(('#', '|', '>', '-', '*'))]
text = ''.join(body)
sents = [x for x in re.split(r'(?<=。)', text) if x.strip()]
lens = [len(x) for x in sents]

print(f"文数 {len(sents)} / 平均 {statistics.mean(lens):.1f}字 "
      f"/ 標準偏差 {statistics.pstdev(lens):.1f} / 最短 {min(lens)} / 最長 {max(lens)}")
print(f"30字未満 {sum(1 for l in lens if l < 30) / len(lens) * 100:.0f}% ｜ "
      f"30-50字 {sum(1 for l in lens if 30 <= l <= 50) / len(lens) * 100:.0f}%（AIっぽさの帯）")

vague = ['大幅に', '多くの場合', 'さまざま', '様々', 'いくつか', '比較的', 'かなり',
         '非常に', 'ある程度', '適切に', '基本的に', '一般的に', 'かもしれません',
         'と思われます', '重要です']
cliche = ['この記事では', 'について解説します', '近年', '注目を集め',
          'ではないでしょうか', 'いかがでした', '順に見ていきます', '見ていきましょう']
scaffold = ['説明します', 'まとめておきます', 'ここからは', '必要があります']
for label, words in [('曖昧表現', vague), ('定型句', cliche), ('足場の文', scaffold)]:
    hits = [f'{w}×{text.count(w)}' for w in words if w in text]
    print(f"{label}: {', '.join(hits) if hits else 'なし'}")
EOF
```

### 合格ライン

| 指標 | 目安 | 外れたときの直し方 |
| --- | --- | --- |
| 標準偏差 | **25 以上** | 短文で断定する行を足す。長文は具体例の列挙なら残してよい |
| 30字未満の割合 | **20% 以上** | 同上 |
| 30〜50字の割合 | **40% 未満** | ここが AI の素の長さ。膨らんでいたら分割か削除 |
| 曖昧表現 | **0** | 数字に置き換える。測っていないなら「約○倍」「○割」で範囲を出す |
| 定型句 | **0** | 冒頭を結論・問題提起・数字のどれかにする |
| 足場の文 | 少ないほどよい | 「順に見ていきます」は消しても意味が通る |

## 1. 体験を 1 つ足す

**一番サボりがちで、一番効く。** 測定値だけ並ぶと報告書になる。

入れるのは、**実際にやったから書けること**に限る。捏造はしない。

- ○「そのまま拝借するつもりでしたが、念のため動かす前に署名だけ検証しました。そこで止まりました」
- ○「ここだけは早送りができないので、ターミナルを開いたまま 1 時間待ちました」
- ✕「とても驚きました」 — 感想だけで情報がない
- ✕ 実際にはやっていない手順や、抱いていない感想

最低 1 つ。計測が多い記事ほど、手を動かした痕跡を 2〜3 箇所に散らす。

## 2. 数字を具体化する

「大幅に速くなった」ではなく「26.2 µs/op」。
正確な値が無いなら「約 2 倍」「3 割減」のように範囲で出す。

この repo の記事は実測が売りなので、ここは元から強いはず。
**監査スクリプトで曖昧表現が 1 つでも出たら、そこは測り忘れている。**

## 3. 1 文を削る

AI は説明を**足す**方向に伸ばす。読者が推測できることは書かない。

削る候補:

- 「順に見ていきます」「まとめておきます」— 足場。消しても通る
- 直前の表が示したことを、文章で言い直している段落
- 「〜という意味で先に潰しておく必要があります」のような、理由の後置き説明

> 迷ったら消してみて、意味が通るなら消したまま出す。

## 4. 文の長さにバラツキを出す

AI 生成文は 30〜50 字が等間隔に並ぶ。**短文で断定し、長文で具体例を列挙する。**

長い文そのものは悪くない。技術的な列挙（claim 名、エラーコード、条件）が
入っているなら 100 字超でも読める。**揃っていることが問題。**

## 5. 冒頭の定型句を消す

書かない:

- 「この記事では○○について解説します」
- 「近年、○○が注目を集めています」
- 「○○に興味がある方は多いのではないでしょうか」

この repo はエピグラフ 1 行から入る骨格（`structure.md`）なので、
**エピグラフを定型句にしないこと**が実質の要件になる。結論・問題提起・数字のどれかで入る。

- ○ `> 実装は、ちゃんと動きました。壊れていたのはドキュメントの方です。`
- ○ `> あなたのアプリ、v5 にしたら壊れますか。僕のは壊れました。`

締めも同じ。「いかがでしたか」で終わらない。
