## 1. 初回同期でAPIリクエスト数と待ち時間を減らした

**判定: 作者の実測記録に記載。外部から同じGitHubアカウント・期間での再計測はしていない。**

- [`how-to-be-more-fast.md`](how-to-be-more-fast.md) §1 は、実アカウントの初回30日同期について0.1.0の295秒 / 2,015リクエストと、0.1.1の124秒 / 952リクエストを記録している。
- 同節は改善要因を、PR・コミット・Issue段階の並列化、未変更Issueの取得省略、headコミットのCI結果をGraphQLへ統合、同時リクエスト数の既定値を4から8へ、と分けている。
- [段階を並列化したコミット](https://github.com/tanahiro2010/ghusage/commit/073495c)、[Issue取得を省いたコミット](https://github.com/tanahiro2010/ghusage/commit/e65bf72)、[CI結果をGraphQLに統合したコミット](https://github.com/tanahiro2010/ghusage/commit/3fb30b0)、[並列数を変更したコミット](https://github.com/tanahiro2010/ghusage/commit/8505b40)。
- 記録では、並列4から8への変更単独の比較は180秒から124秒、リクエスト数は952で一致。全施策前後の295秒から124秒とは比較条件が異なるため、混同しない。

### 記事に使える切り口

- まずリクエスト数自体を減らし、その後に並列度で待ち時間を縮めた。API回数の削減と並行実行の効果を別の話として説明する。

## 2. 同じ程度のAPIリクエストで差分同期を短縮した

**判定: 作者の公開版比較記録。再試行で完全性を保つ対応も含む。**

- [`how-to-be-more-fast.md`](how-to-be-more-fast.md) §3 は、差分30日同期の公開版比較を記録している。v0.1.4は15.0秒、14.5秒（平均14.8秒）。v0.1.5は5.8秒、5.1秒、7.8秒（平均6.2秒）。各版2〜3回の比較で、広い統計的な結論ではない。
- 同じ比較表のAPIリクエストはv0.1.4が45〜47回、v0.1.5が46〜47回。回数の削減ではなく、直列に待っていたページ取得と検索段階の重なりが主な改善。
- [検索ページ並列化](https://github.com/tanahiro2010/ghusage/commit/d7105bc)、[RESTページ並列化](https://github.com/tanahiro2010/ghusage/commit/2c6b834)、[コミット検索の同時開始](https://github.com/tanahiro2010/ghusage/commit/18383a3)。
- 並列取得でGitHubの検索応答が`incomplete_results: true`になることがあり、[不完全ページの再取得](https://github.com/tanahiro2010/ghusage/commit/21b4634)を追加。記録上、間隔を空けた4回の同期はすべてcompleteで、再取得は1回発生した。
- 速度比較は同条件の完全なベンチマークではなく、実アカウントでの少数回測定。本文では「約2.4倍」として記録の範囲にとどめる。

### 記事に使える切り口

- リクエスト数がほぼ同じでも、依存関係をほどいて待ち時間を重ねると短くなる。並列化後の完全性を再試行とCoverageで扱った点も一緒に説明する。

## 3. キャッシュ集計は実行計画とホットパスを直した

**判定: 作者の実測・プロファイル記録。SQLiteの一般的な説明は公式資料も参照。**

- [`how-to-be-more-fast.md`](how-to-be-more-fast.md) §2 は、10万イベントのDebugベンチにおいて7日集計がOS別に131〜173秒から1〜2秒、30日が169〜240秒から3秒になったと記録している。
- [SQLite `SELECT` ドキュメント](https://www.sqlite.org/lang_select.html)には、SQLiteの`CROSS JOIN`が通常の結合順序最適化を抑止し、左テーブルを外側のループに置くための制御として使えることが説明されている。個別の速度結果は作者の計測値であり、SQLite公式の保証値ではない。
- [実行計画修正コミット](https://github.com/tanahiro2010/ghusage/commit/4ff1ddf)。記録によれば、`EXPLAIN QUERY PLAN`で統計未作成時にアカウントの全イベントをPRごとに走査する計画を確認し、`CROSS JOIN`で`parent_pr_id`の索引を使う順に固定した。
- [自分のPRだけ過去履歴を読む変更](https://github.com/tanahiro2010/ghusage/commit/14f2122)の後、CI releaseランナーの7日p95は654msから226ms。
- [列を位置で読む変更](https://github.com/tanahiro2010/ghusage/commit/efd2a81)後は、CI記録の7日p95が145ms、30日p95が223ms。記事の比較値「643ms→145ms」は別箇所の記録値と10ms差がある（§2-2の654msと§2-3の643ms）。記事で比較値を出す場合、比較表の「CIランナー、同じランナーで比較」643ms→145msを採用し、§2-2の654msは別の計測記録として扱うか、数値の出所を再確認する。
- M4での7日 / 30日p95は93.8 / 126.2ms（release、ウォームアップ5回の後50回）と記録。

### 記事に使える切り口

- SQLのプラン修正の後にも、プロファイルでRust側の列名検索がホットパスだと分かった。既出SQLite記事を詳説し直すより、「改善後に次のボトルネックが移った」話に絞る。

## 4. CIの所要時間は段階を分けて説明する

**判定: 作者のCI実行記録。数値は各段階の累積改善であり、すべて同じブランチ・条件とは限らない。**

- [`how-to-be-more-fast.md`](how-to-be-more-fast.md) §7 は、SQLite集計修正の副次効果としてCI全体が約13分から約8分、ジョブ分割後は約8.3分から6.7分、OS別チェック整理とWindows linker変更後は6.7分から5.0分、dev pushでrelease buildを省いた後は5.0分から3.0分と記録している。
- [ジョブ分割](https://github.com/tanahiro2010/ghusage/commit/890624f)、[OS別チェックとrust-lld](https://github.com/tanahiro2010/ghusage/commit/c33e010)、[devでrelease buildを省略](https://github.com/tanahiro2010/ghusage/commit/524e175)。
- **3分はdevブランチへのpushでrelease buildがskipされた実行**。全ブランチ、release向けCI、すべてのPRで3分になるという意味ではない。
- 同じ記録は、入力が同じ再実行を検証済み成果で省略するケースを11.6分から約25秒としている。これは一般のCI実行短縮ではなく、同一入力の再利用に限定した値。
- GitHubの[Workflow runs REST API](https://docs.github.com/en/rest/actions/workflow-runs)は実行や所要時間の参照手段を説明している。ただし、公開されているGitHub APIから当該run IDや比較条件はこの調査では再取得できていない。

### 記事に使える切り口

- CIで実行時間の長いジョブを測り、同一入力で再利用できる処理やdevでは不要なrelease buildを省いた。単に並列数を増やした結果として書かない。

## 5. 不採用の最適化と測定上の制約

**判定: 作業記録で確認。**

- SQLiteページキャッシュを32MiBに広げる変更は、負荷の高い環境で測定値が2〜6倍揺れ、効果を判断できず取り消した（[`how-to-be-more-fast.md`](how-to-be-more-fast.md) §2-4）。
- TLSライブラリのAWS-LCからringへの変更はrelease clean build 62秒から56秒という記録だが、暗号ライブラリを変える便益に見合わないと判断し、不採用（同 §9）。この値は単一条件のビルド計測であり、実行時速度を示さない。
- ベンチマーク比較で変更のない処理に約10%の差が出た事例が記録されている（同 §10-3）。固定順の基準版・PR版測定が環境差や順序の影響を受けた可能性は記録上の推測で、原因が実証済みとは書かない。

### 記事に使える切り口

- 効果を判定できなければ採用しない。測定ノイズを、改善の成果として扱わない。

## 数値を記事に使うときの注意

- 実測値は作者のローカル記録から転記したもの。独立再現した値として紹介しない。
- 初回同期の295秒→124秒は複数施策をまとめた前後比較。並列度単独の比較は180秒→124秒。
- 差分同期14.8秒→6.2秒は公開版の少数回平均。APIリクエスト数はほぼ同じ。
- SQLiteの131〜173秒→1〜2秒は**Debugベンチ**で、一般ユーザーのrelease実行時間の比ではない。
- 7日p95の643ms→145msはCIランナーの記録比較。M4の93.8msとは環境を混ぜない。643ms / 654msの不一致に注意。
- CI約13分→約3分は複数の累積変更で、最終値はrelease buildを省略したdev push。
- 採用済み、試したが不採用、未実施の候補を区別する。
