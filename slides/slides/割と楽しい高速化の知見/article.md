> 自分で作ったCLIなのに初回同期に5分かかる。まずログを見ました。

## この記事の結論

GitHubの活動を集計するCLI、ghusageの初回同期は30日分で295秒かかっていました。API呼び出しを減らし、ページ取得を並列にし、SQLiteとCIも見直しました。

| 同期 | 変更前 → 変更後 |
| --- | ---: |
| 初回30日 | 295秒・2,015回 → 124秒・952回 |
| 差分30日 | v0.1.4平均14.8秒 → v0.1.5平均6.2秒、リクエスト数はほぼ同じ |

ソースコードはこちらです: https://github.com/tanahiro2010/ghusage

**295秒を124秒にしても、話は終わりませんでした。** APIの呼び出しを減らした次は、差分同期のページ待ちが残りました。SQLiteを直した後も列名の検索が集計時間に残り、CIではその集計テストがジョブを止めていました。

> OSC Osaka 2027で話すghusageの高速化について、スライドに入れなかった測定条件や、採用しなかった案もここに残します。RustでCLIを作っていて、遅い場所をどう探すか悩んでいる人に向けた記事です。数値は作業記録から転記しており、独立した環境で再現した値ではありません。

---

## 1. 初回同期で5分待った

ghusageは、GitHubでのコミット、Pull Request、レビュー、コメント、CIなどを同期し、期間ごとに集計するCLIです。同期したデータはローカルのSQLiteに保存します。

M4上で実アカウントの30日分を初回同期すると、295秒かかりました。APIリクエストは2,015回です。初めて使う人に5分待ってもらうのは長い。

同期ではGitHubからPRやコミットを検索し、Issueの詳細やCI状態を補ってからローカルDBへ保存します。295秒という合計時間だけでは、ネットワークの回数が多いのか、依存する段階を順番に待っているのか、保存後の集計が遅いのかを切り分けられません。

最初に見たのは、全体の所要時間とリクエスト数、それからリクエストごとの開始・終了時刻です。「遅い」という感想だけでは、APIの回数が多いのか、通信を直列に待っているのか、ローカル処理が詰まっているのかが分かりません。そこで同期をJSON形式で実行し、`api.requests`とGitHubクライアントのdebugログを並べました。

手元ではこのコマンドを使いました。

```sh
GHUSAGE_LOG=ghusage_github=debug ghusage sync --format json
```

JSONの`api.requests`から総リクエスト数を見て、debugログではリクエストごとの`elapsed_ms`を追います。後で差分同期を調べるときは、終了時刻から開始時刻も逆算して時系列に並べました。まず全体の数、その後に内訳です。

ログを追うと、前回から更新されていないIssueの詳細まで取り直していました。前回の取得が完全で、検索結果の`updated_at`も同じなら、詳細を再取得しません。前回の取得が不完全なときは省略せず、同期カーソルも進めません。次の同期で取り直せます。

Pull Requestのheadコミットに付いたCI結果も、PRごとにREST APIで取得していました。実装記録ではPR 1件につきPR本体、check runs、commit statusesの計3リクエストです。PRを取るGraphQLクエリにCI結果を含め、statusesがある場合だけRESTに戻す形に変えました。

全部のREST呼び出しをなくしたわけではなく、GraphQLの応答に必要なステータスが含まれない場合は従来のREST取得を残し、欠けた情報を取れる経路も維持しています。

こうした取得の省略や同期段階の並列化を重ね、初回同期は295秒から124秒、リクエスト数は2,015回から952回になりました。これは複数変更をまとめた前後比較です。295秒から124秒の差を、ひとつの修正の成果として説明することはできません。

リクエスト数を減らす変更と、同時実行数を増やす変更は分けて考えました。同じ30日分を並列数4と8で比べた記録では、952リクエストのまま180秒から124秒に短縮し、集計値も一致しました。リクエスト数を半減させた施策の効果と、通信の待ちを重ねた効果を混ぜないためです。

既定の同時リクエスト数は4から8へ変えています。上限は16のままです。並列数を変えた後も`overview`の数値が一致したことを確認してから既定値にしました。並列化は仕事の順番を変えるので、結果が同じかも比較します。

もう一つ、毎回の同期自体を省く変更も入れました。直前の同期から5分以内なら、2回目の`weekly`や`daily`では同期をせず、最後に同期した時刻までのデータでレポートを出します。これは同期を速くするのではなく、短時間に繰り返しレポートを開く利用者の待ちをなくす工夫です。

レポートの期間を最後に同期した時刻までに切り詰めることで、まだ取得していない時間帯までデータがあるように見せずに済みます。最新データを必ず取りたい場合は`--max-age 0`でこの省略を無効にできます。


待っている間の表示も変えました。同期中は何も出ず、止まっているように見えたため、端末では2行の進捗を上書き表示します。300ms以内に終わる処理では表示せず、パイプ出力も汚しません。並列化した後は、実際に動いているHTTPリクエストの数と名前も表示するようにしました。時間は同じでも、何を待っているかは分かるようになりました。

この表示はログを大量に流すものではありません。端末の同じ2行を更新し、同期が終われば消します。JSONをパイプへ流すときは出ません。まず「検索中なのか」「何件中何件まで進んだか」が分かるようにし、その後、同時に動いているリクエストを表示しました。

## 2. コミット検索の7秒はページ待ちだった

初回同期の次に気になったのは、普段使いの差分同期でした。APIの無駄を減らした後も、30日分の同期に約15秒かかります。デバッグログから各リクエストの開始・終了を並べると、コミット検索の9ページを1ページずつ取りにいき、約7秒を直列に使っていました。

ログの時刻を並べるとこうなります。

```text
0.5–2.2s   /search/issues ×3
2.2–3.5s   /graphql (PR)
3.3–10.5s  /search/commits ×9  ← ここが直列
10.5–11.9s /repos/*/commits        (並列)
11.7–14.1s /repositories/<id>/commits ×6 (直列)
```

PR検索と重なっている時間もあれば、1ページ目の応答を待ってから2ページ目を要求している時間もあります。総時間だけではこの区別がつかず、リクエストの開始・終了時刻を置いて初めて直列部分が見えました。

この時系列を作るため、ログの`elapsed_ms`と終了時刻から開始時刻を逆算しました。単純にログの出力順だけを見ると、並行で動いているリクエストと直列の待ちが混ざって見えるからです。

検索APIの1ページ目には`total_count`が含まれます。最大1,000件までの検索結果を100件ずつ取得するため、2ページ目以降を同時に取りにいけます。RESTのページングも応答の`Link`ヘッダーから最後のページが分かる場合は、途中のページを並列に取得しました。ページURLは一から作らず、ホスト検査を通ったリンクのページ番号だけを書き換えます。結果が増えて最後のページに次ページのリンクが付いていれば、続きもたどります。


さらに、コミット検索はPR検索の完了を待つ必要がありませんでした。PRのリポジトリ一覧が必要になるのは、後からdefault branchのコミットを取得するときだけです。そこでコミット検索を先に開始し、リポジトリ一覧が必要な箇所だけで合流するようにしました。

つまり、処理を全部いっせいに走らせたのではなく、依存関係のないコミット検索とPR検索を並べ、PRの結果が必要になるdefault branchの取得だけを後から待つ形です。

比較はnpmで公開したv0.1.4とv0.1.5を、同じ実アカウント・同じ30日間で交互に実行したものです。版ごとの測定は2〜3回で、90秒ずつ空けました。

| 公開版 | 差分同期 | APIリクエスト |
| --- | ---: | ---: |
| v0.1.4 | 平均14.8秒 | 45〜47回 |
| v0.1.5 | 平均6.2秒 | 46〜47回 |

およそ2.4倍の短縮ですが、測定回数は少数です。少なくともこの比較では、呼ぶ回数を減らしたのではなく、直列に待っていた時間を重ねたことが主な違いでした。

初回同期は同じようには縮みませんでした。v0.1.4は97.9秒でpartial、v0.1.5は109.9秒でcompleteです。両方とも検索APIのレート制限による待ちが入り、検索回数を減らさない限り初回の時間は改善しないと記録しています。

つまり、差分同期のページ待ちを重ねる変更は初回同期の律速には効きませんでした。認証済み検索の呼び出し上限に達して待つ状態では、ページを並列にしても検索そのものの回数が残るからです。

並列化には副作用もありました。GitHubの検索APIが`incomplete_results: true`を返すことが増え、並列化前は3回中0回、並列化後は約5回中2回で不完全な結果が出た記録があります。速くても、検索結果が欠けたまま同期を完了したら困ります。


不完全なページは指数バックオフで最大2回取り直します。それでも不完全ならCoverageをpartialとして残し、その範囲の同期カーソルを進めません。間隔を空けた4回の同期ではすべてcompleteになり、そのうち1回は再取得が起きました。速度の数字だけではなく、結果がそろったかも見ています。

検索結果が欠けた状態で同期カーソルだけ進むと、次回の同期がその範囲を取りに戻らないため、再試行の上限に達した後もpartialという状態をデータベースに残す必要がありました。

### 変更行数は通常同期に詰め込まなかった

コミットの追加行数と削除行数も欲しくなりました。REST APIでコミットを1件ずつ取得すると、1,000件で1,000リクエストになります。そこで通常の同期からは分け、必要なときにだけ次のコマンドを実行する設計にしました。

```sh
ghusage sync --diff-stats
```

PRに含まれるコミットの行数は、もともとPRを取るGraphQLクエリに含められます。それ以外は100件ずつまとめて取得します。生成するクエリは、リポジトリとコミットに別名を付ける形です。

```graphql
query CommitLineCounts {
  r0: repository(owner: "octo", name: "app") {
    c0: object(oid: "<full-commit-sha>") {
      ... on Commit { additions deletions }
    }
  }
}
```

`<full-commit-sha>`は実装上40桁のSHAに置き換わります。owner、repository name、SHAはGraphQL文字列へ埋め込む前に形式を検査します。実アカウントの7日分では1,153コミット中472件をPRクエリへの相乗りで取得し、追加リクエストは0でした。残り681件は必要なものだけをバッチで取り、1,147件で約12リクエストという記録があります。2回目は取得済みの行数を使うため再取得しません。

### コミットのdiffも一度取ればいい

TUIではPull Requestからコミットのdiffを開けます。以前は開くたびにGitHubへコミット詳細を取りにいき、ファイル数が多ければページングも発生しました。取得したメッセージ、親コミット、ファイル一覧、diffはSQLiteの`commit_details`に保存します。2回目からはキャッシュで開けるので、ネットワークがなくても表示できます。初回取得は別スレッドで行い、読み込み中もTUIのキー操作を止めません。

## 3. JOINを直した後に残った列名検索

API同期を見直している途中で、CIの`cargo test`がOSによって6〜8分かかることに気づきました。ワークフローの並列数を増やす前にログを分解すると、ベンチマークのテストモードでキャッシュから7日分を読む処理が131〜173秒、30日分が169〜240秒かかっていました。

これは10万イベントを使った**Debugビルドの計測**です。配布用releaseビルドの通常の実行時間ではありません。ですが、CIのテストを止めているのは確かでしたし、利用者が大きなキャッシュから集計するときにも同じ処理が走ります。

PRごとのイベントを集めるクエリは、元はこの形でした。

```sql
SELECT {EVENT_COLS} FROM activity_events e
JOIN account_events ae ON ae.event_id = e.event_id
WHERE ae.account_id = ?1 AND e.parent_pr_id = ?2
```

インデックスはありました。問題は、SQLiteがどちらのテーブルから読み始めるかでした。統計がない状態では`account_events`を先に走査し、そのアカウントに属するイベントをPRごとに探す計画になっていました。

```text
-- JOINのまま
SEARCH ae USING PRIMARY KEY (account_id=?)
SEARCH e USING INDEX ... (event_id=?)
```

10万イベントを1回読むだけならここまでかかりません。アカウント全体のイベント走査をPRごとに繰り返したため、PR数との掛け算になっていました。`CROSS JOIN`に変えてSQLiteの結合順を固定すると、`parent_pr_id`のインデックスからイベントを取る計画に変わりました。

```sql
SELECT {EVENT_COLS} FROM activity_events e
CROSS JOIN account_events ae ON ae.event_id = e.event_id
WHERE e.parent_pr_id = ?2 AND ae.account_id = ?1
```

```text
-- CROSS JOIN
SEARCH e USING INDEX activity_events_parent_pr (parent_pr_id=?)
SEARCH ae USING COVERING INDEX account_events_event (event_id=? AND account_id=?)
```

このJOIN順序の話は、[別の記事でEXPLAIN QUERY PLANと計測を詳しく書きました](https://blog.tanahiro2010.com/articles/sqlite-join-order-ghusage/)。ここで追いたいのは、Debugベンチが1〜3秒になった後です。

7日分は1〜2秒、30日分は3秒になりました。CI全体も記録上約13分から約8分に短縮しました。

実行計画を調べると、統計がない状態ではアカウントの全イベントを先に読み、その処理をPRごとに繰り返していました。10万イベントを一度読むだけなら大きな負荷ではありませんが、PR数との掛け算になっていました。

7日分のrelease集計は、CIランナーでp95 654msから226msになりました。それでも当時の目標200msを超えています。そこで、当てずっぽうにSQLを変えるのではなく、macOSでベンチマークを動かし続けて`sample`のプロファイルを取りました。

上位には`rusqlite::RowIndex::idx`や`columnName`、文字列比較の関数が並んでいました。イベント1行あたり約20列を、行ごとに列名で探しています。クエリごとに一度だけ列の位置を調べ、各行では位置で読む形に変えました。

変更後の読み出しは、列の場所をprepare時に一度だけ作り、行ごとの変換に渡します。

```rust
let mut stmt = conn.prepare(sql)?;
let cols = EventCols::of(&stmt)?;
let mut rows = stmt.query(params)?;

while let Some(row) = rows.next()? {
    out.push(cols.event(row)?);
}
```

`EventCols::of`の中で`stmt.column_index("event_type")`などを呼び、`event_type`の列番号を記録します。各行では名前でなく番号を渡します。

```rust
let ty: String = r.get(self.event_type)?;
```

列名から位置を引く処理自体は小さく見えますが、1行で約20列、それを期間内のイベント行ごとに繰り返すため、集計全体ではプロファイルの上位を占めていました。

同じCIランナーの記録では、7日p95が226msから145ms、30日が223msになりました。変更前後9種類の集計結果とPR詳細3件がバイト単位で一致することも確認しています。M4でのrelease計測はウォームアップ5回の後50回で、7日93.8ms、30日126.2msです。環境の違う値を一つの前後比較として混ぜてはいけません。

期間より前のイベントを読む必要があるのは、自分が作ったPRの「最初のレビューまでの時間」などを計算するときだけでした。他の人のPRは期間内のイベントだけでよいため、過去履歴の読み込み対象を自分のPRに絞り、`overview`や`reviews`など9種類の出力が変更前とバイト単位で同じことを確認しました。

なお、7日p95の記録には別の箇所に643msと654msの両方が残っています。145msという改善後の値は同じですが、前値の差は解消できていません。比較表にある643msと、別のベンチ記録の654msを混ぜずに書いています。

## 4. Actionsを並列化する前にテストを見た

最初は「Actionsを並列にすれば短くなるか」と考えました。しかし、テスト内で一回の集計が2分以上かかっているなら、まず製品の処理を直すほうが効きます。SQLiteのJOIN修正だけでCIが約13分から約8分になったのは、その副次効果でした。


その後も、CIの仕事を分けていきました。テストとrelease buildを別ジョブにすると、全体は約8.3分から6.7分へ。プラットフォームに依存しない重い確認をUbuntuに集約し、Windowsで`rust-lld`を使うと約5分になりました。温まったキャッシュで測り直した結果、Windowsのテストは4.2分から2.8分、macOS Intelは6.5分から3.1分になっています。最初の実行はキャッシュキーが変わって依存を再ビルドし、12.1分に延びました。キャッシュが温まった状態の計測も必要でした。最後にdev pushではrelease buildを省き、記録上3分まで短縮しました。

テストをすべてのOSから外したわけではありません。OSに依存しないfmtと性能系テストだけをUbuntuに寄せ、WindowsやmacOSで分岐するコードを含むclippyと通常のテストは各OSに残しました。WindowsのテストバイナリをリンクするMSVCリンカーは、Rustに同梱される`rust-lld`へ置き換えました。

この3分はdev pushの値です。release向けPRでも同じ時間になるわけではありません。release buildはrelease向けの検証に残しています。

同じ入力で成功済みのCIをもう一度走らせる場合は、入力ファイルの組み合わせをハッシュ化し、検証済みならジョブの中身を省く仕組みも作りました。同じ内容の再実行は11.6分から約25秒になりました。これは初回CIの所要時間ではなく、以前と同じ入力を再利用したケースです。

ジョブごとに必要な入力ファイルを列挙し、そのファイル群の内容からキャッシュキーを作ります。成功したジョブはOSごとに検証済みの印を残し、次回は同じキーがあるかを調べて処理を省きます。必須チェックとしては成功を返す必要があるので、ジョブ自体を消すのではなく中の作業だけをスキップします。

入力一覧が空なら失敗させます。空の一覧でハッシュを計算すると、変更を一度も検証していないのに「検証済み」と誤判定するからです。workflowの核はこの程度のシェルです。

```bash
files=$(git ls-files -s -- "$@")
test -n "$files" || { echo "no inputs matched: $*" >&2; exit 1; }
printf '%s\n' "$files" | sha256sum | cut -c1-40
```

さらに、pushを重ねたときに古いCIを最後まで走らせないよう、同じブランチやPRに新しい実行が来たら前の実行を取り消します。無関係なコミットを止めるのではなく、同じ対象の古いチェックを止めます。

CIのやり直しを減らすため、テストの不安定さも直しました。タイムアウト試験で確認したいのはクライアントの再試行回数です。遅いランナーでサーバーにリクエストが何回届いたかを厳密に期待すると、最後の試行が届く前に期限が切れて失敗することがありました。クライアント側の再試行回数を検証し、期限も300msから1秒へ変えました。確認したい上限はそのままです。

以前は300ms以内に応答が届く前提のテストでしたが、Windowsランナーでは同じ試行が4回しか届かない場合と9回届く場合があり、テストしたい再試行ロジックより環境の遅さを測っていました。

release buildはdev pushのたびには走らせません。release向けPRとreleaseブランチではビルドし、devへのpushではテストとclippyを続けます。workflowの条件はこうです。

```yaml
build:
  if: >-
    (github.event_name == 'pull_request' && github.base_ref == 'release')
    || github.ref == 'refs/heads/release'
```

この条件を入れた後のdev pushが約3分でした。release向けの検証を外して3分にしたわけではありません。

## 5. 試して戻したもの

最適化を試しても、採用しなかった変更があります。

SQLiteのページキャッシュを32MiBに広げました。プロファイルでファイル読み込みが目立ったためです。しかし、手元の負荷が高く、測定値が2〜6倍揺れて効果を判定できませんでした。設定は戻しました。測定環境を整えずに、たまたま出た速い数字を成果にしないためです。

プロファイルでは`pread`やメモリコピーも上位に残っていましたが、CLIは1回の実行で集計を一度読み込むだけです。ページキャッシュを大きくして効くのはTUIで何度も再読み込みする場面に限られると考え、効果を確認できないまま常時使う設定にはしませんでした。


ビルド時間も`cargo build --timings`で内訳を調べました。手元のclean buildはdevで44秒、releaseで62秒。大きな部品は`aws-lc-sys`のビルドスクリプトでした。TLSライブラリをAWS-LCからringに変える実験では、release clean buildが62秒から56秒になりましたが、dev buildは44秒のままでした。暗号ライブラリを変えるほどの効果とは判断せず、採用していません。これはビルド時間の話で、実行時性能の改善ではありません。

releaseではこのほかに`libsqlite3-sys`のビルドが21秒、LTOを含む最終リンクが16秒かかっていました。開発ビルドでは差分ビルドが約8秒なので、毎日の編集ループを変える候補はclean buildの一番大きな部品と同じとは限りません。

差分のテストビルドはもともと約8秒で、デバッグ情報の設定を変えても7.8秒から8.4〜10.8秒となり、改善したとは言えませんでした。ビルドの内訳を見ると、AWS-LCは並行して進んでいて開発ビルド全体の律速ではなかったことも分かりました。

ベンチマークにも揺れが出ました。変更していない集計処理が、基準版とPR版の比較で約10%遅く見えたことがあります。基準版を先に測る順序の影響などが候補ですが、原因は確定していません。今後の候補として、基準版とPR版を交互に測る方法を考えています。

この比較を手元の負荷に任せないよう、release向けPRでは同じGitHub Actionsランナーで基準版とPR版を測り、Criterionの中央値やp95、変化率をコメントに出すworkflowも用意しました。0.1.2のPRでは基準版の集計が遅すぎて60分の上限に達し、0.1.3では7日p95が654msから145ms、30日が806msから223msになった記録があります。同じマシンで測っても、固定順で測る偏りまでは消えません。

## 6. 初回同期はまだ検索待ち

初回同期では、APIリクエストの数が多すぎました。差分同期では、件数よりページングの直列待ちが効いていました。APIの後はSQLiteの実行計画と行の読み出しが問題になり、そこを直すとCIの実行時間も縮みました。

原因を探すたびに、見るものも変わりました。API同期では`api.requests`とリクエストの時刻、SQLiteでは`EXPLAIN QUERY PLAN`と`sample`のプロファイル、CIではjobの開始・終了時刻です。数字を一つ見て全部を決めるのは無理でした。

差分同期は短くなりました。それでも初回同期では検索APIのレート制限が待ちを作っています。v0.1.4は97.9秒でpartial、v0.1.5は109.9秒でcompleteでした。検索ページの並列化だけではここは速くなりません。次に試すのは、初回同期で検索APIを呼ぶ回数を減らすことです。
