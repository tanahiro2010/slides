## 1. 便利なCLIを作ったら、最初の同期に5分かかった

- ghusageの用途: GitHub上での自分の活動をローカルに同期し、期間別に集計する。
- 初回30日同期（実アカウント、Apple M4 macOS）

  | | v0.1.0 |
  | --- | ---: |
  | 所要時間 | 295秒 |
  | APIリクエスト | 2,015回 |

- 1リクエストの処理だけでなく、検索、詳細取得、CI情報取得などAPIを何度も呼ぶ設計全体が待ち時間を作っていた。
- 最初に確認するものを「遅い」という感想で終わらせず、同期時間・リクエスト数・リクエスト別ログに置いた。
- 着地: 何を改善するかを決める前に、遅さの場所と仕事量を見えるようにする。

## 2. 不要なAPI仕事を減らす

- まず初回同期の処理を棚卸しした。
- 見つかった重複・省略可能な取得
  - 更新されていないIssueの詳細を、同期のたびに再取得していた。
  - PRごとにRESTで取得していたheadコミットのCI結果を、PRのGraphQLクエリに統合できた。
  - PR・コミット・Issueの同期段階は一部を並行して進められた。
- Issueは、前回完全取得した`updated_at`と検索結果が一致すれば取り直さない。完全取得でなかった場合はカーソルを更新せず、次回に再取得する。
- CI情報をGraphQLに統合し、statusesが存在しない場合だけREST取得を省略する。GraphQLに収まらない場合のfallbackも残す。
- 初回同期の合計比較

  | | v0.1.0 | v0.1.1 |
  | --- | ---: | ---: |
  | 所要時間 | 295秒 | 124秒 |
  | APIリクエスト | 2,015回 | 952回 |

- これは複数施策をまとめた前後比較。並列度変更単独の比較は並列4で180秒、並列8で124秒（いずれも952リクエスト）。
- 着地: 速くする前に、そもそも不要な仕事をしていないか確認する。

## 3. リクエスト数をほぼ変えずに、待ち時間を重ねる 🔥

- 初回同期後も、30日差分同期が約15秒かかっていた。
- GitHub APIのdebugログから、リクエストの開始・終了時刻を並べて待ち方を調べた。
  - 検索ページが1ページずつ直列に進み、コミット検索だけで約7秒かかる区間があった。
  - RESTのコミット一覧も最後のページまで直列に待っていた。
  - コミット検索はPR検索の終了を待っていたが、最初の検索自体はPR結果に依存しない。
- 依存関係を保ったまま並行化
  - 検索結果の総数から対象ページを求め、2ページ目以降を同時取得。
  - RESTの`last`ページが得られた場合、2ページ目から最後まで同時取得し、ページ順に結合。
  - コミット検索とPR検索を同時に始め、PR由来リポジトリ情報が必要な箇所だけ待つ。
- v0.1.4とv0.1.5の公開版比較（実アカウント、各2〜3回）

  | | v0.1.4 | v0.1.5 |
  | --- | ---: | ---: |
  | 差分同期の平均 | 14.8秒 | 6.2秒 |
  | APIリクエスト | 45〜47回 | 46〜47回 |

- 平均の元データはv0.1.4が15.0 / 14.5秒、v0.1.5が5.8 / 5.1 / 7.8秒。少数回なので性能一般の保証値ではない。
- 🔥 API回数がほぼ同じでも、通信の依存関係を整理すれば待ち時間を短縮できた。
- 着地: 並列化の効果は、仕事量の削減とは別に測る。

## 4. 速くても、検索結果が欠けたら成功ではない

- ページ並列化後、GitHub Search APIが`incomplete_results: true`を返すことが増えるケースを観測。
- 不完全な結果を正常完了として保存すると、同期が速くても活動データを落とす。
- 対応
  - 不完全と判定した検索を指数バックオフ付きで再試行。
  - 再試行しても取得できない場合はCoverageをpartialとして記録し、完全に取れたように見せない。
  - 不完全なまま同期カーソルを進めない。
- `how-to-be-more-fast.md`の記録では、間隔を空けた4回の同期はすべてcomplete。うち1回で再取得が発生。
- この回数は少数の実アカウント同期であり、APIが常に完全な結果を返すという証明ではない。
- 着地: 性能改善の成功条件に、データの完全性を含める。

## 5. SQLiteを直した後、行の読み方が次のボトルネックになった

- 背景: SQLiteの実行計画修正で、10万イベントを使うDebug集計が7日131〜173秒から1〜2秒になった。SQLの詳細は過去記事で扱ったため、ここでは短く紹介。
- その後も集計に余地があり、CI releaseランナーの7日分p95が200ms目標を超えていた。
- まず「期間中に動いたPR」の過去履歴をすべて読む必要があるかを確認。
  - 過去の履歴が時間指標に必要なのは自分が作成したPRだけ。
  - 対象を自分のPRに絞り、9種類の集計出力で修正前後がバイト一致することを記録。
  - 7日p95は654msから226msへ。
- まだ残る時間をプロファイリング。
  - Rust SQLite bindingの列名検索が行ごとに呼ばれ、文字列比較に時間を使っていた。
  - ステートメントごとに列位置を一度だけ調べ、各行では位置で読む形に変更。
- 最終的な計測記録

  | 環境・期間 | p95 |
  | --- | ---: |
  | CIランナー・7日 | 145ms |
  | CIランナー・30日 | 223ms |
  | Apple M4・7日 / 30日 | 93.8ms / 126.2ms |

- 7日CIランナーの前値は別の記録に643msと654msがある。145msという後値は一致するが、前値の差の原因は未確認。記事で643ms→145msを使うなら元の比較表に限定し、この揺れは注記する。
- 着地: DBを速くしても、読み出した後の変換処理が次の支配的コストになることがある。改善のたびに測り直す。

## 6. CIの高速化はクリティカルパスと不要な仕事を見る

- CI全体が約13分かかり、テストを含む集計ベンチがOSによって6〜8分を占めていた。
- 最初にCIを並列化するより、テストで走る製品集計自体を計測。
  - SQLite修正により重いベンチが短縮。
  - CI全体は記録上、約13分から約8分へ。
- 次にworkflow構成を見直した。
  - テストとrelease buildを別ジョブにする: 約8.3分から6.7分。
  - 重いプラットフォーム非依存チェックを1 OSに集約し、Windowsでrust-lldを利用: 6.7分から5.0分。
  - dev pushではrelease buildを実施しない: 5.0分から3.0分。
- 3分はrelease buildがskipされたdev pushの実測。release向けCIの全体時間ではない。
- 同じ入力の検証済み成果を再利用する仕組みでは、同内容の再実行が11.6分から約25秒になった。通常の初回CIと同一視しない。
- 着地: CIの時間を短くするには、並行実行だけでなく、実行不要な作業・重複作業を見つける。

## 7. 効果を確かめられなかった案は採用しなかった

- SQLiteのページキャッシュを32MiBに拡大
  - `pread`が目立つプロファイルから、ファイル読み込みを減らせると考えた。
  - マシン負荷が高く、測定結果が2〜6倍にばらついた。
  - 改善効果を判断できず、設定を取り消した。
- AWS-LCからringへの変更
  - release clean buildが62秒から56秒という手元計測。
  - 暗号ライブラリを変更するコストに見合わないと判断し不採用。
  - clean build時間の値であり、アプリの実行時性能を示さない。
- ベンチマーク順序
  - 固定順で基準版・変更版を測り、変更していない処理にも約10%差が出た事例。
  - 環境差や測定順の影響は原因候補であり、確定した原因として説明しない。
- 🔥 「速くなったように見えた」では採用せず、測定条件が整わないなら保留・撤回する。
- 着地: 最適化の一部は、効かなかった案を捨てる判断。

## 8. ボトルネックは移動する。次に測る場所を決める

- 今回の変化
  - APIリクエスト数が大きい → 不要な取得と重複を削減。
  - リクエスト数を減らした後も待つ → ページングとタスク依存を並列化。
  - 集計が遅い → 実行計画を直し、読み込む履歴を絞り、Rust側のホットパスを計測。
  - CIが遅い → 製品ベンチの時間を直し、workflowの重複と不要なbuildを整理。
- 高速化で持ち帰った判断手順
  1. 症状を時間・リクエスト数・プロファイルなどで見えるようにする。
  2. 仕事量、待ち時間、データ読み込み、実行構成のどこに原因があるかを仮説にする。
  3. 一度に変える対象を絞り、前後で性能と正確性を確かめる。
  4. 効果を判断できない変更は保留または撤回する。
- 締め: 速いコードを書くことと、速いプログラムを作ることは同じではない。計測すると、次に直す場所が見えてくる。
