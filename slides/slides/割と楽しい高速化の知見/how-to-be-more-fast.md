# 高速化の施策の全記録(0.1.0 リリース後 〜 0.1.5、2026-11-22)

0.1.0(npm 初公開、9b71a80 相当)から 0.1.5 までに入れた、速さに関わる施策をすべてまとめる。本体(同期・キャッシュからの集計・TUI・取得方式)と CI / CD の両方を含む。

各施策は次の形で書く(2-4 以外の不採用案と 10 章の未実施案を含め、すべての施策に 5 項目をそろえた)。

- **該当箇所**: 変更したファイル・関数・設定
- **ペイン**: 何が遅く、誰がどう困っていたか(数値つき)
- **着想**: どこに目を付け、なぜそこだと考えたか
- **ソース**: 判断の根拠にしたもの(実測ログ、プロファイル、実行計画、CI のジョブ時間、ドキュメントなど)
- **ソリューション**: 何をどう変えたか
- **結果**: 実施後の実測
- **コミット**: 該当コミットのハッシュ(dev / release に入っている)

数値はすべて実測。測った環境を書く。「手元」は Apple M4 の macOS、「CI ランナー」は GitHub Actions のホストランナー。

## 1. 同期の高速化 第 1 弾(0.1.1)

### 共通の背景

- **ペイン**: 0.1.0 で実アカウント(tanahiro2010、PR・コミットが非常に多い)の 30 日分を初めて同期すると **295 秒、API リクエスト 2,015 回**。差分同期でも **20 秒 / 55 リクエスト**。レポートを開くたびに同期が走るので、毎回 20 秒待つ。ユーザーから「実行に時間がかかりすぎる」「取得の並列実行も」「実行時間がネック」と指摘。
- **ソース**: 実アカウントでの同期の実測(`sync --format json` の `api.requests`、所要時間)、`GHUSAGE_LOG=ghusage_github=debug` のリクエストログ。記録: tasks/PROGRESS.md、tasks/reports/real-api/2026-11-22-ci-counts.md。

### 1-1. PR・コミット・Issue の段階を同時に進める

- **該当箇所**: crates/ghusage-app/src/sync.rs(`run`、`Shared`、`search_prs` / `fetch_prs` / `sync_issues` / `sync_commits`)
- **ペイン**: 同期は「PR を探す → PR を取る → コミットを探す → Issue を探す → Issue を取る」を 1 つずつ順に進めていた。各段階の中は並列でも、段階の間は待ち合わせになっていて、ネットワーク待ちが積み重なっていた。
- **着想**: PR・コミット・Issue は互いの結果をほとんど使わない(コミットの段階が PR のリポジトリ一覧を使うだけ)。段階どうしを同時に走らせれば、待ち時間が重なる。同時に動かしても、HTTP クライアントのセマフォが同時リクエスト数を抑えるので GitHub への負荷は増えない。
- **ソース**: デバッグログのリクエストの時系列で、段階ごとに完全に直列になっていることを確認。
- **ソリューション**: 段階を `tokio::try_join!` で同時に実行。SQLite の `Store` は 1 本のタスクの中で `RefCell<&mut Store>` として共有し、`await` をまたいで借用を持たないようにした(スレッドをまたがないので `Send` 不要、ロックも不要)。
- **結果**: 1-2〜1-4 と合わせて計測(下の「第 1 弾の結果」)。
- **コミット**: `073495c`

### 1-2. 変わっていない Issue を取り直さない

- **該当箇所**: crates/ghusage-app/src/sync.rs(`sync_issues`、`issue_cursor`)、SyncReport の `issues_unchanged`
- **ペイン**: 検索で見つかった Issue を、毎回すべて GraphQL で取り直していた。差分同期でも、変わっていない Issue の取得が大半。
- **着想**: 検索結果には `updated_at` がある。前回完全に取得したときの `updated_at` と同じなら、新しい履歴はない。PR では同じ仕組み(`pr_sync_states`)があったのに、Issue にはなかった。
- **ソース**: 差分同期のリクエストの内訳(Issue の詳細取得が多い)。
- **ソリューション**: Issue ごとに同期カーソル `issue_updated_at:<node_id>` に「完全に取得できたときの更新時刻」を保存し、一致すれば取得を省く。不完全な取得では保存しない(次回取り直す)。`--full` では省かない。
- **結果**: 変わっていない Issue の取得がゼロに(`issues_unchanged` として報告)。
- **コミット**: `e65bf72`(表示 `1720a8d`)

### 1-3. head コミットの CI 結果を PR のクエリに統合する

- **該当箇所**: crates/ghusage-github/src/queries.rs(`PullRequestDetail`)、crates/ghusage-github/src/pull_request.rs
- **ペイン**: PR 1 件ごとに、GraphQL の本体クエリに加えて REST の check-runs と statuses の 2 リクエスト、計 3 リクエストかかっていた。PR が数百件あると、これだけで数百リクエスト。
- **着想**: GraphQL の `checkSuites { checkRuns }` で同じ情報が取れる。commit statuses は「1 件もない」ことが GraphQL の `status: null` で分かるので、そのときは REST を呼ばなくてよい。
- **ソース**: リクエストの内訳(`/check-runs`、`/statuses` が PR の数だけ並ぶ)。GraphQL と REST の項目対応(check run の id = REST の node_id、permalink = html_url など)を突き合わせ、イベントの ID・種類・時刻・結果が変わらないことを確認。
- **ソリューション**: PR のクエリで head コミットの check suites / check runs(`checkType: ALL` で再実行分も含む)を取り、statuses がある場合だけ REST を呼ぶ。GraphQL に収まらない量のときは REST の `filter=all` に戻る。
- **結果**: statuses のない PR は 3 リクエスト → **1 リクエスト**。2,015 → 952 リクエストの大部分。実 API の 12 PR で、REST だけの値と件数が一致することを確認(tasks/reports/real-api/2026-11-22-ci-counts.md)。
- **コミット**: `3fb30b0`

### 1-4. 同時リクエスト数の既定を 4 → 8 に

- **該当箇所**: src/cli.rs(`--concurrency` の既定)、crates/ghusage-app/src/sync.rs(`SyncOptions::new`)
- **ペイン**: 1-1〜1-3 の後も、同時 4 本ではネットワーク待ちが残っていた。
- **着想**: GitHub は同時リクエストに 100 本の目安を示しており、8 本なら二次レート制限に触れない。並列数で数値が変わらないこと(冪等性)も確かめられる。
- **ソース**: 同じアカウント・同じ期間で並列 4 と並列 8 を実測し、overview の数値が完全一致することを確認。
- **ソリューション**: 既定を 8 に(上限 16 は据え置き)。
- **結果**: 初回 30 日同期 **並列 4: 180 s / 952 req → 並列 8: 124 s / 952 req**。数値は完全一致。
- **コミット**: `8505b40`

### 1-5. 直前の同期を再利用する(`--max-age`)

- **該当箇所**: src/main.rs(`prepared_session`)、src/cli.rs(`--max-age`、環境変数 `GHUSAGE_MAX_AGE`)、crates/ghusage-app/src/session.rs(`synced_until`)
- **ペイン**: `ghusage weekly` のあとに `ghusage daily` を打つだけで、また同期が走って十数秒待つ。
- **着想**: 数分前に同期したなら、新しいデータはほとんどない。レポートの期間を「最後に同期した時刻」までに切り詰めれば、同期せずにキャッシュだけで正しく答えられる(カバレッジの正直さも保てる)。
- **ソース**: 利用の流れ(同じ期間のレポートを続けて開く)の観察。
- **ソリューション**: 最後の同期が `--max-age`(既定 5 分)以内なら同期を省き、期間の終わりを同期済みの時刻に切り詰めて表示し、その旨を表示。`--max-age 0` で常に同期。
- **結果**: 5 分以内の 2 回目以降のレポートは **同期なしで即座に表示**(キャッシュからの集計時間だけ)。
- **コミット**: `a33f9e9`

### 第 1 弾の結果

| 計測(実アカウント、30 日、手元) | 0.1.0 | 0.1.1 |
|---|---|---|
| 初回同期 | 295 s / 2,015 req | **124 s / 952 req**(並列 4 では 180 s) |
| 差分同期 | 20 s / 55 req | 約 14〜21 s |
| 5 分以内の 2 回目のレポート | 毎回同期 | 同期なし |

差分同期の残りは、コミット検索のページ送り(1 ページ 100 件)と検索 API の上限待ちだと分かった(→ 第 2 弾の 3 章)。

## 2. キャッシュからの集計の高速化(0.1.2 〜 0.1.3)

### 背景: 気づかないうちに遅くなっていた

- 独立監査で、`prs --details` の時間指標(最初のレビューまでの時間など)が期間内のイベントだけで計算される不具合(D2)が見つかり、**`0e04820`** で「期間内に動いた PR は、期間より前のイベントも読み込む」ように直した。
- 性能の記録(7 日 p95 34.7 ms)はこの修正の**前**の測定のままで、修正後に測り直していなかった。実際にはこの修正で、期間内に動いた PR の全履歴を読むようになり、読み込みが大きく遅くなっていた。

### 2-1. 実行計画の修正(CROSS JOIN)

- **該当箇所**: crates/ghusage-storage/src/lib.rs(`load_dataset_inner` の PR ごとのイベント取得、`pr_events_sql`)
- **ペイン**: 最初の症状は CI。`cargo test` が OS によって 6〜8 分かかり、CI 全体で約 13 分。内訳を見ると、テストに含まれるベンチマークのテストモードで「キャッシュから 7 日分を読む」1 回が **131〜173 秒**、30 日分が **169〜240 秒**。利用者の環境でも、キャッシュが大きいほど `weekly` などが遅くなる性質のもの。
- **着想**: 1 回の読み込みが分単位なのは、件数に比例する遅さではなく、掛け算で効いている。PR ごとに投げるクエリが索引を使っていないのではと疑った。
- **ソース**:
  - CI ログのタイムスタンプ(`Testing cached 7-day aggregation` から `Success` まで 2 分 11 秒)
  - SQLite の `EXPLAIN QUERY PLAN`: `SEARCH ae USING PRIMARY KEY (account_id=?)` → `SEARCH e USING INDEX sqlite_autoindex...(event_id=?)`。統計(ANALYZE)がないと、SQLite は `account_events` 側から結合を始め、**PR 1 件ごとにアカウントの全イベントを走査**していた(PR 数 × イベント数)。`ANALYZE` 後は `activity_events_parent_pr` 索引を使う計画になることも確認。
- **ソリューション**: `JOIN` を `CROSS JOIN` に変えて結合順序を固定(SQLite では CROSS JOIN が順序の指定になる)。左に `activity_events` を置き、`parent_pr_id` の索引から引く。返る行は同じ。実行計画が索引を使うことをテストで固定(修正前のクエリでテストが失敗することを確認)。
- **結果**:

| CI ランナー(デバッグビルド、10 万イベント、1 回) | 修正前 | 修正後 |
|---|---|---|
| ubuntu 7 日 / 30 日 | 131 s / 169 s | **2 s / 3 s** |
| macOS 7 日 / 30 日 | 173 s / 240 s | **1 s / 3 s** |
| Windows 7 日 / 30 日 | 133 s / 172 s | **2 s / 3 s** |

  副次効果で CI の `cargo test` が 364〜588 s → 78〜204 s、CI 全体が約 13 分 → 約 8 分(6 章)。

- **コミット**: `4ff1ddf`(0.1.2)

### 2-2. 期間より前の履歴は自分の PR だけ読む

- **該当箇所**: crates/ghusage-storage/src/lib.rs(`load_dataset_inner`)
- **ペイン**: 0.1.2 をリリースビルドで測ると、キャッシュから 7 日分の集計が **p95 253 ms**(手元)、**654 ms**(CI ランナー)で、PRD の目標 **200 ms** を超えていた。
- **着想**: 期間より前の履歴が必要なのは時間指標だけで、時間指標は**自分が作った PR**についてしか計算しない(`timing_stats` の `pr.author.is(subject)`)。他人の PR の過去まで読む必要はない。ベンチマークのデータ(1 年 2,000 PR、イベントを PR に順繰りに割り当て)では、7 日でもほぼ全 PR が「期間内に動いた」扱いになり、ほぼ全件を読んでいた。
- **ソース**: 時間指標の利用箇所の洗い出し(`timing_stats`、`pr_timing` の呼び出し元。PR 詳細は別の読み込み `load_pr_dataset` を使う)。
- **ソリューション**: 履歴を読む対象を「期間内に動いた PR のうち、作成者が自分のもの」に絞る。手元の実キャッシュで、`overview`、`prs --details`(`--all-participants` 含む)、`reviews`、`comments`、`daily`、`repos` の 9 通りの出力が修正前とバイト一致することを確認。他人の PR の過去イベントが読まれないことをテストで固定。
- **結果**: CI ランナー(release、同じランナーで基準と比較)で **7 日 p95 654 → 226 ms**、30 日 830 → 349 ms。まだ 200 ms を超えていた。
- **コミット**: `14f2122`(0.1.3)

### 2-3. イベントの列を名前でなく位置で読む

- **該当箇所**: crates/ghusage-storage/src/lib.rs(`EventCols`、`query_events`。旧 `event_from_row`)
- **ペイン**: 2-2 の後も CI ランナーで 7 日 226 ms。
- **着想**: 推測で直さず、プロファイルを取る。
- **ソース**: macOS の `sample` で、ベンチマークの「cached 7-day」だけを 120 秒回している最中の定常状態を採取。上位は `rusqlite::RowIndex::idx`(1,114)、`columnName`(967)、`_platform_strlen`(693)、`_platform_memcmp`(657)など。**イベント 1 行あたり約 20 列を、行ごとに列名で探していた**(`r.get("event_type")` が毎回全列名と文字列比較)ことが支配的だった。
- **ソリューション**: クエリごとに 1 回だけ列の位置を求める `EventCols::of(&stmt)` を作り、行は位置(`r.get(idx)`)で読む。出力は 9 通り + PR 詳細 3 件でバイト一致を確認。
- **結果**:

| 計測 | 0.1.2 | 0.1.3 | 目標 |
|---|---:|---:|---:|
| CI ランナー 7 日 p95(同じランナーで比較) | 643 ms | **145 ms** | 200 ms |
| CI ランナー 30 日 p95 | 806 ms | **223 ms** | 500 ms |
| 手元 M4 7 日 / 30 日 p95(release、ウォームアップ 5 + 50 回) | — | **93.8 / 126.2 ms** | 200 / 500 ms |

- **コミット**: `efd2a81`(0.1.3)

### 2-4. SQLite のページキャッシュを広げる(検討して採用しなかったもの)

- **該当箇所**: crates/ghusage-storage/src/lib.rs(`configure`。一時的な変更で、元に戻した)
- **ペイン**: 2-3 の後も、キャッシュから 7 日分の読み込みに時間がかかっていた(手元の負荷下で 128 ms 前後)。
- **着想**: 2-3 の後のプロファイルで、残りの上位が `pread`(1,019)と `_platform_memmove`(1,545)だった。SQLite が毎回ファイルからページを読み直しているので、既定 2 MiB のページキャッシュを広げれば減るのではと考えた。
- **ソース**: macOS の `sample` によるプロファイル(2-3 の修正後、cached 7-day を 120 秒回した定常状態)。
- **ソリューション**: `PRAGMA cache_size = -32768`(32 MiB)を接続設定に追加して計測。
- **結果**: 手元の負荷平均が 16〜69 と高く、計測値が 2〜6 倍に揺れて効果を判断できなかったため、**取り消した**。CLI は 1 回の実行で 1 回しか読まないので効果は TUI の再読み込みに限られる。静かな環境での再計測を今後の候補とした(10-4)。
- **コミット**: なし(取り消し)

## 3. 同期の高速化 第 2 弾(0.1.5)

### 共通の背景

- **ペイン**: 30 日の差分同期が約 15 秒。CI 結果の統合などで要求数は減ったが、時間はまだかかる。
- **ソース**: `GHUSAGE_LOG=ghusage_github=debug` のログから、リクエストごとの開始・終了時刻を並べた時系列(各リクエストの `elapsed_ms` と終了時刻から開始時刻を逆算)。

```
0.0-  0.3s  /user
0.5-  2.2s  /search/issues ×3
2.2-  3.5s  /graphql(PR)
3.3- 10.5s  /search/commits ×9   ← 1 ページずつ直列(全体の約半分)
10.5- 11.9s  /repos/*/commits(並列)
11.7- 14.1s  /repositories/<id>/commits ×6 ← 1 リポジトリを直列
```

### 3-1. 検索の 2 ページ目以降を並列に取る

- **該当箇所**: crates/ghusage-github/src/search.rs(`search`、`get_page`)、crates/ghusage-github/src/http.rs(`page_of`、`with_page`)
- **ペイン**: コミット検索 9 ページを `Link: rel="next"` で 1 ページずつたどり、約 7 秒(差分同期の半分)。差分同期でも、取りこぼし防止のため直近 3 日分を取り直すので、活動の多いアカウントでは毎回 900 件・9 ページになる。
- **着想**: 検索の 1 ページ目に `total_count` があるので、ページ数は最初に分かる。2 ページ目以降を同時に取れる。URL は自分で組み立てず、1 ページ目の `next` リンク(ホストの検査を通ったもの)の `page` だけを書き換えれば、別ホストへのリンクを拒否する既存の安全確認がそのまま効く。
- **ソース**: 上の時系列、GitHub の検索 API の仕様(1 ページ 100 件、上限 1,000 件)。
- **ソリューション**: `pages = ceil(min(total, 1000) / 100)` を求め、2〜N ページを `try_join_all` で同時取得(同時数はトランスポートのセマフォで制限)。取得中に結果が増えて最後のページに `next` があれば、続けてたどる(テストあり)。
- **結果**: 30 日差分同期 約 15 s → **約 9 s**(9.1 s / 9.3 s)。
- **コミット**: `d7105bc`

### 3-2. REST のページを `rel="last"` まで並列に取る

- **該当箇所**: crates/ghusage-github/src/http.rs(`get_paginated`、`link`、`parse_link`)
- **ペイン**: 時系列の末尾、1 つのリポジトリのデフォルトブランチのコミット 6 ページを直列に取り、約 2.4 秒。
- **着想**: REST の `Link` ヘッダーには `rel="last"`(最後のページ)も入っている。3-1 と同じ方法で途中のページを同時に取れる。
- **ソース**: 同上の時系列、GitHub REST のページ送りの仕様。
- **ソリューション**: 1 ページ目に `next`(page=2)と `last` があれば、2〜last を同時に取得し、ページ順に結果を並べる。`last` がない応答は従来どおり 1 ページずつ。
- **結果**: 末尾の直列待ち(2.4 s)が並列に(3-3 の結果に含む)。

### 3-3. コミット検索を PR 検索と同時に始める

- **ペイン**: 3-1 の後の時系列で、コミット検索は PR の検索・取得が終わるまで始まらなかった(コミットの段階が PR のリポジトリ一覧を受け取ってから始まる作りのため)。

## 4. 変更行数の取得方式(0.1.5、Issue #8)

- **該当箇所**: crates/ghusage-github/src/line_counts.rs(`fetch`、`fetch_batch`、`query`)、crates/ghusage-github/src/queries.rs(PR クエリと `PrCommitFields`)、crates/ghusage-app/src/sync.rs(`fetch_line_counts`)
- **ペイン**: (設計時に避けたもの)コミットの追加・削除行数は検索結果に含まれない。REST の「コミット 1 件取得」なら 1 コミット 1 リクエストで、1,000 件あれば 1,000 リクエスト。Issue でも「通常の同期に大量のリクエストを入れない」ことが要件。
- **着想**:
  - GraphQL ではエイリアスで 1 クエリに多数のオブジェクトを並べられる(`r0: repository(...) { c0: object(oid: "...") { ... on Commit { additions deletions } } ... }`)。
  - PR のコミットは、すでに PR のクエリで取っているので、そこに `additions deletions` を足せば追加リクエストなしで取れる。PR の差分(`additions deletions changedFiles`)も同じ。
- **ソース**: GitHub GraphQL の Commit オブジェクトの項目、REST の Get a commit の仕様、実 API での計測。
- **ソリューション**:
  - PR のクエリに行数の項目を追加(相乗り、追加 0 リクエスト)。
  - それ以外は `sync --diff-stats` で、行数がまだないコミットだけを 100 件 1 クエリにまとめ、複数のクエリを並列に取得。取得済みは取り直さない。名前と SHA は厳密に検査してから埋め込む(クエリへの注入を防ぐ)。
- **結果**:
  - 実アカウント 7 日: 1,153 コミットのうち **472 件は PR クエリへの相乗りで 0 リクエスト**、残り 681 件も `--diff-stats` で数リクエスト。
  - 1,147 件で約 12 リクエスト(バッチの並列化前は約 27 秒、並列化後は 258 件を数リクエストで約 10 秒の同期に含めて取得)。独立監査では 392 件で 4 リクエスト。
  - 2 回目は取得済みを再利用して 0 リクエスト。
- **コミット**: `76ff644`(PR クエリへの相乗り)、`4491b3b`(`--diff-stats` とバッチの並列化)

### 5-1. 2 行の進捗表示(0.1.1)

- **該当箇所**: src/progress.rs(新規。`Progress`、`State::apply`、`frame`、描画スレッド `paint`)、crates/ghusage-app/src/sync.rs(`SyncProgress::Detail` の通知)、src/main.rs(同期の呼び出し)

- **着想**: 実時間は変えられなくても、進んでいることが見えれば待てる。ただしログを流すとレポートの出力が汚れ、スクリプトでも邪魔になる。端末のときだけ、決まった 2 行を上書きで描き、終わったら消せばよい。速い同期では何も出さないほうがよい。
- **ソース**: ユーザーの要望文、同期の各段階で何をしているか(検索、PR の取得、リポジトリのコミット一覧)の通知点の洗い出し。

- **結果**: 同期中に、どの段階が何件中何件まで進み、直前に何を取ったかが常に見える。レポートの出力やパイプには何も残らない(テストで確認)。
- **コミット**: `a33f9e9`

### 5-2. 並列で動いているリクエストの表示(0.1.5)

- **該当箇所**: crates/ghusage-github/src/activity.rs(新規。`Activity`、`ActivitySnapshot`、`Running`、`label`)、crates/ghusage-github/src/http.rs(`attempt` で記録)、crates/ghusage-github/src/lib.rs(`GitHubClient::activity`)、src/progress.rs(`frame`、`redraw`)、src/main.rs

## 7. CI の高速化

ジョブ時間はいずれも GitHub Actions のジョブの開始・終了時刻から計算(`gh run view --json jobs`)。ステップ内の内訳は CI ログのタイムスタンプから。

### 7-1. 検証済みの入力を省き、古い実行を取り消す

- **該当箇所**: .github/workflows/ci.yml(`inputs` ジョブ、各ジョブの `ci-verified-*` キャッシュ、`concurrency`)
- **ペイン**: ドキュメントだけの変更や、dev で検証済みのコミットを release に取り込む PR でも、全 OS で全工程(約 11.6 分)が走った。push を重ねると古い実行も最後まで走った。
- **着想**: CI が検証するのは「入力ファイルの内容」。内容が同じなら、同じ OS で一度成功していれば再実行は不要。必須チェックは「成功」を返す必要があるので、ジョブ自体は残して中身だけ省く。
- **ソース**: ユーザーの要望(「変更ないならスキップとかキャッシュとか」)、CI の実行履歴。
- **ソリューション**: `inputs` ジョブでジョブごとの入力ファイル群の `git ls-files -s` のハッシュを作り、成功したら `ci-verified-<job>-<os>-<hash>` という空のキャッシュを保存。次回、同じキーがあれば処理を飛ばして成功を返す(ファイル一覧が空ならエラーにして、誤って全部スキップすることを防ぐ)。同じブランチ・PR の新しい push で古い実行を取り消す。依存のキャッシュは失敗時も保存。
- **結果**: 内容が同じ再実行が **11.6 分 → 約 25 秒**。release 向け PR が dev で検証済みのコミットなら、ほぼ即時に必須チェックを満たす。
- **コミット**: `5fda838`

### 7-2. 集計の修正による副次効果

### 7-3. テストと release build を別ジョブに

- **ペイン**: 7-2 の後、CI 全体は約 8.3 分で、最も遅い Windows と macOS Intel のジョブが全体を決めていた。両者とも fmt・clippy・test・release build を 1 ジョブの中で順番に実行していた。

### 7-4. プラットフォームに依存しない重い確認は 1 OS で、Windows は rust-lld

- **該当箇所**: .github/workflows/ci.yml(`test` ジョブ。`FULL_OS`、条件付きのステップ、`CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_LINKER`)
- **ペイン**: テストのジョブで Windows 4.2 分、macOS Intel 6.5 分が全体を決めていた。ユーザーから「テストの実行時間、特に Windows と macOS Intel がボトルネック」「cargo fmt は一つの環境で検証すれば多分それでいい(ただ環境差もあるのでここはどうするか)」「Win の Test に時間がかかっているのでここの対策を」と指摘。
- **着想**:
  - 最適化なしのビルドで 10 万イベントを扱う性能系のテストを全 OS で走らせても、性能の数字としては意味がない(正式な性能はリリースビルドのベンチマークで測る)。中身もプラットフォームに依存しない。1 つの OS で動くことを確かめれば十分。
  - fmt の結果は OS に依存しない(rustfmt は改行コードをファイルのまま扱う)。一方 clippy は、Unix と Windows で分かれるコード(`cfg(unix)` のシグナル処理やファイル権限)があるので各 OS に残す。
  - Windows はテストバイナリ 33 本のリンクに標準の MSVC リンカーを使っていて遅い。Rust のツールチェーンに同梱の `rust-lld` が使える。
- **ソース**: CI ログのタイムスタンプからのテストステップの分解:

| | Windows | macOS Intel |
|---|---:|---:|
| テストのコンパイル | 84 s | 116 s |
| ベンチマークのテストモード | 37 s | 62 s |
| TUI の 10 万イベント応答性テスト | 18 s | 28 s |
