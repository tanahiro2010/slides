
# ghusage Performance Optimization v2 — PRD

**Status:** Draft / Implementation Ready after Baseline Verification  
**Target:** ghusage v0.1.2以降  
**Repository:** <https://github.com/tanahiro2010/ghusage>  
**Base Branch:** `dev`  
**Release Branch:** `release`  
**Date:** 2026-11-22

---

## 1. Executive Summary

ghusageは、GitHub上の開発活動を正確に集計・分析するRust製CLI/TUIアプリケーションである。

v0.1.2までの改善によって、30日分の初回同期が295秒から124秒、APIリクエスト数が2,015回から952回になった。

また、SQLiteの非効率なJOIN順序を修正したことで、10万イベント規模のデバッグビルドでの集計時間が、macOSでは173秒から1秒まで短縮された。

本プロジェクトの目的は、これらの改善を維持しながら、次の性能上の制約を解消することである。

1. GitHub検索APIのレート制限に起因する同期遅延
2. コミット検索および取得時のページング負荷
3. CIに残るビルド・テストの直列実行
4. 大規模キャッシュに対する読み込み・集計コスト
5. 巨大PRの取得コストと処理時間
6. 性能回帰を継続的に発見するための検証体制

**最重要原則：高速化のために集計結果の正確性を犠牲にしない。**

## 3. Goals / Non-Goals

### 3.1 Goals

- 同じデータを、より少ない時間で取得する
- 不要なAPIリクエストを削減する
- キャッシュ規模による性能劣化を抑制する
- CIの結果取得までの実時間を短縮する
- 性能回帰を自動的に検出する
- CLI/TUIで一貫した結果を維持する
- Rate Limitを尊重する
- 大規模データでも安全に動作する

### 3.2 Non-Goals

- 新しいGitHub指標の追加
- 指標定義の変更
- データの推測による補完
- 既存のキャッシュ形式の全面刷新
- GitHub APIの利用規約に反する取得
- 精度と引き換えの不完全な高速集計
- OSサポートの削減
- テストそのものの無条件削除

## 5. Phase 0 — Performance Baseline

### PERF-001: 計測基盤の構築

**目的**

最適化前の実行時間を処理段階ごとに正確に把握する。

**要件**

- 同期全体の実行時間を記録
- PR検索時間
- Issue検索時間
- コミット検索時間
- コミット一覧取得時間
- PR詳細取得時間
- SQLite読み込み時間
- SQLite書き込み時間
- 集計時間
- APIレスポンス待機時間
- レート制限待機時間
- APIリクエスト数
- リトライ回数

計測は単調増加時計を用いる。

計測機能のオーバーヘッドは実用上無視できる水準とし、ベンチマークによって確認する。

**Acceptance Criteria**

- 全体時間と各段階の時間が確認できる
- 並列処理の時間を単純加算して全体時間と誤認しない
- 計測の有効・無効で集計結果が一致する
- トークンやプライベート情報を記録しない
- 計測結果をJSONで機械的に比較できる

**実装方針**

既存の`ApiStats`と同期レポートを拡張可能か調査する。新しい計測基盤を追加する前に、既存の集計機能との重複を確認する。

## 6. Phase 1 — GitHub API Optimization

### PERF-010: API待機時間の可視化

**現状**

GitHub APIの検索には独立したレート制限があり、既存コードではレート制限応答に対する待機・リトライが実装されている。

しかし、処理段階別の実際の待機時間については、新たなベースラインが必要である。

**要件**

- REST、Search、GraphQLの統計を分離
- リクエストの実行時間を計測
- 待機時間を計測
- レート制限に起因する待機を区別
- ネットワーク遅延とローカル処理時間を区別
- Secondary Rate Limitを検出した場合の挙動を検証

**禁止事項**

レート制限を回避するための認証情報のローテーションや、過剰なリクエスト発行は実装しない。

### PERF-011: Adaptive Concurrency

**仮説**

すべてのAPIに同じ並列数を使用することが、必ずしも最適ではない。

**調査内容**

- Search APIとREST APIで並列度を分離する効果
- 同時実行数とリクエスト完了時間の関係
- Rate Limit応答と並列度の関係
- APIごとのキューイングの有効性

**実装候補**

APIファミリーごとに制御可能なセマフォまたはスケジューラを導入する。

ただし、計測で改善が確認できない場合は実装しない。

**Acceptance Criteria**

- 無制限の同時実行が発生しない
- 既定値8の既存動作との比較がある
- Rate Limitを受けた際にリクエストが集中しない
- 再試行に上限がある
- API数・時間・失敗率を比較できる
- 既存の`--concurrency`を破壊しない

### PERF-012: コミット検索の最適化

**背景**

コミット検索は最大100件単位でページングされ、大規模アカウントで取得時間が伸びる。

**調査項目**

1. 現在の検索クエリの分割方法
2. 期間分割による追加APIコスト
3. 不必要な再検索の有無
4. 既存Coverageの再利用可能性
5. コミット一覧取得との重複
6. APIごとの待機比率

**候補**

- 既知の完全取得範囲の再利用改善
- 検索結果とリポジトリコミット一覧の処理重複削減
- 更新が必要な範囲だけへの問い合わせ
- 安全なページング処理の改善

**重要な制約**

GitHub検索のインデックスはすべてのコミットを保証しない。

現在のリポジトリ一覧による補完を削除してはならない。

### PERF-013: Conditional Requests

GitHubの条件付きリクエストを利用できる箇所について、ETag等による再取得回避を検証する。

**実装条件**

- 対象APIが条件付きリクエストに対応する
- キャッシュ済みレスポンスを安全に再利用できる
- 304応答を正しく処理できる
- 認証・アクセス権の変化を考慮できる
- データ更新の見落としが発生しない
- レート制限上のメリットを実測できる

改善効果が確認できない場合は不採用とする。

## 7. Phase 2 — SQLite Optimization

### PERF-020: クエリ監査

**目的**

既に修正したJOIN問題以外の性能劣化要因を探す。

**対象**

- 期間指定読み込み
- PRイベントの取得
- リポジトリ別集計
- 日別・週別・月別集計
- Coverage読み込み
- 同期状態の取得

**要件**

- `EXPLAIN QUERY PLAN`を利用する
- 主要なSQLの実行計画を記録する
- インデックスの利用状況を確認する
- 不必要な全表走査を調べる
- N+1クエリを検出する
- データ規模を変えながら計測する

**評価用データ**

- 1万イベント
- 10万イベント
- 100万イベント

それぞれでPR数やイベント分布を変え、偏りのあるデータも用意する。

### PERF-021: SQLite Plannerの比較検証

既存の`CROSS JOIN`による最適化は維持する。

追加で以下を比較する。

- 現状の実行計画
- `PRAGMA optimize`を適切に利用した場合
- 統計情報が存在する場合
- 統計情報が存在しない場合
- データが大きく増えた場合

**Acceptance Criteria**

- `CROSS JOIN`の削除を前提にしない
- 速度が改善することを実測する
- SQLiteバージョン差を考慮する
- キャッシュの互換性を維持する
- クエリの結果が一致する
- 特定のデータ分布だけで速い変更を採用しない

### PERF-022: Cache Loading Optimization

**目的**

TUIとCLIにおける大規模キャッシュ読み込みのコストを減らす。

**調査対象**

- 同じ期間の連続レポート
- 期間切り替え
- リポジトリ切り替え
- TUIタブ移動
- 同一セッション内の再集計

**候補**

- 不変データの再利用
- 集計結果の一時キャッシュ
- 差分再計算
- 必要なデータだけの読み込み
- 不要なデータ変換・複製の削減

**禁止事項**

古い集計結果を最新として扱わない。

## 8. Phase 3 — CI Optimization

### PERF-030: CI Critical Path Reduction

**現状**

`.github/workflows/ci.yml`では、各OSの`check`ジョブ内で以下が直列に実行されている。

1. `cargo fmt`
2. `cargo clippy`
3. `cargo test`
4. `cargo build --release`
5. リリースバイナリのスモークテスト
6. その他プラットフォーム固有テスト

**問題**

テストとリリースビルドが直列であるため、特定OSのジョブがCI全体のクリティカルパスになる。

**改善案**

- Formatting/Lint
- Unit/Integration Tests
- Release Build/Smoke

を、依存関係を考慮したジョブに分離する。

**要件**

- 実測に基づいて分離対象を選ぶ
- テスト・ビルドの必須実行範囲を維持する
- 既存のOSマトリクスを維持する
- 必須チェックをすり抜けない
- ジョブ分離によるランナー利用時間の増加を計測する

**Target**

CI全体の待機時間6分以下。

ただし、ランナー待ち時間と実行時間は分離して評価する。

### PERF-031: Cache Validity Hardening

既存の入力ハッシュ方式を維持しつつ、検証済みキャッシュの正当性を再監査する。

**確認事項**

- Rustコンパイラのバージョン
- Cargo.lock
- 依存関係
- Cargo設定
- ソースコード
- テストコード
- GitHub Actionsワークフロー
- ビルド・テストに使用するスクリプト
- 各種環境変数
- OSおよびアーキテクチャ
- リンカーやビルドフラグ

これらのうち検証結果に影響するものが、キャッシュキーの入力に正しく反映されること。

**Acceptance Criteria**

- 同じ入力の再実行を省略できる
- 未検証の入力は省略されない
- CIが失敗した入力には検証済み印が付かない
- 必須チェックが正しく機能する
- キャッシュ削除後もCIが正常に動作する

### PERF-032: Benchmark CI Reliability

**目的**

性能回帰検出の信頼性を上げる。

**要件**

- Base/Headを同じ環境で比較
- 環境変動による誤判定を抑制
- タイムアウトを明示的に扱う
- 性能改善と回帰を区別
- 比較結果をPRに報告
- ベンチマーク実行環境を記録する

**改善候補**

- A/B/B/Aの交互測定
- 実行順序のバイアス検出
- 複数回測定の中央値
- 統計的ばらつきの記録
- 長時間ベンチマークの分離
- PR用の短時間チェックと定期的な詳細チェックの分離

固定の10%閾値を維持すべきかは、実測したばらつきに基づいて決める。

## 9. Phase 4 — Large-Scale Reliability

### PERF-040: Large PR Testing

数千件のイベントを持つPRで性能と正確性を測定する。

**シナリオ**

- 大量のレビュー
- 大量のインラインコメント
- 長いPRタイムライン
- 多数のコミット
- Force Push
- コメントの編集・削除
- レビュースレッドの解決状態変更

**Acceptance Criteria**

- 無限ページングしない
- メモリ使用量が異常増加しない
- 取得失敗を隠さない
- 正しいCoverageを記録する
- 同期中断後に再開できる
- 重複イベントを作らない

### PERF-041: Memory and Resource Usage

大規模データに対し、以下を測定する。

- 最大RSS
- SQLiteデータベースサイズ
- 集計時のメモリ増分
- TUIのピークメモリ
- 同期時のピークメモリ

最適化によって実行時間を短縮できても、極端なメモリ増加を伴う場合は原則不採用とする。

## 10. Test Strategy

### 10.1 Correctness Tests

最適化の前後で以下を比較する。

- Commits
- PRs
- Reviews
- Comments
- Issues
- CI関連指標
- Coverage
- JSON出力
- CSV出力
- TUIの集計結果

時刻、順序、状態などを含め、既存仕様に従った完全一致を要求する。

次の環境で評価する。

- Linux x64
- Linux arm64
- macOS Apple Silicon

以下を意図的に発生させる。

復旧後に正しい集計ができることを確認する。

## 11. Agentic Implementation Plan

### Stage A — Investigation

Agentは最初に現在のGitHubソースを読み、既存の最適化内容を確認する。

必須成果物：

- 現在の構造の整理
- 処理段階別の性能計測
- ボトルネックランキング
- 既存の対策との重複調査
- 最適化候補と予想されるリスク

調査なしに性能改善コードを実装してはならない。

### Stage B — Experiment

各改善候補について、変更前のベースラインを保存してから小さな実験を実施する。

必須成果物：

- 仮説
- 変更内容
- 実験環境
- 性能測定結果
- APIリクエスト数
- メモリ使用量
- 正確性検証結果

改善が確認できない場合は変更を採用しない。

### Stage C — Implementation

採用した改善を本実装へ統合する。

要件：

- 既存アーキテクチャを尊重する
- 差分を必要最小限にする
- テストを追加する
- 公開APIの互換性を保つ
- ドキュメントを更新する
- 回帰テストを整備する

### Stage D — Independent Verification

実装担当Agentと別の検証担当による独立評価を行う。

検証担当は実装担当の成功報告を証拠として扱わない。

自らソース・実行結果・測定ログを確認する。

## 13. Agent Execution Rules

1. 計測せずに性能改善を主張しない。
2. テストを削除して高速化しない。
3. エラーを握りつぶさない。
4. 不完全なデータを完全と表示しない。
5. API制限の回避を実装しない。
6. 元の計測ログを保存する。
7. 性能改善のために集計定義を変更しない。
8. CIの成功を製品の正確性の唯一の証拠にしない。
9. 大きな変更を一度にまとめず、改善ごとに検証する。
10. 完了条件を満たさない場合は未完了として報告する。

**性能目標をすべて達成することより、正確で再現性のある改善を行うことを優先する。**

## 15. Definition of Done

ghusage Performance Optimization v2は、次の条件を満たしたときに完了とする。

**既存の正確性・安全性・互換性を保ちながら、計測可能な性能改善を実現し、その改善が独立した検証によって再現可能であること。**

性能目標が達成できなかった場合、未達の原因が外部API制限などに由来すると実測で説明でき、かつ残る改善候補が記録されていれば、その項目は制約付き完了として扱える。ただし、Functional Gates、Correctness Gates、Quality Gatesの不合格は許容しない。
