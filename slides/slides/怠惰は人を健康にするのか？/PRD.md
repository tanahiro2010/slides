# 1. プロジェクト概要

## 1.1 コンセプト

エンジニアリングにおける三大美徳の一つ「怠惰」。

将来の面倒を減らすため、今のうちに工夫し、自動化し、仕組みをつくる。その姿勢はエンジニアの美徳とされてきた。

一方、ヘルスケアの文脈ではどうだろうか。

人間が努力しなくてもよくなることは、必ずしも健康につながるとは限らない。

人間の能力を技術で補完することと、人間自身の能力を使わなくなることは、同じなのだろうか。

この問いを、開発中のコミュニケーション支援プロジェクト「E.D.I.T.H」を具体例として考察する。

## 1.2 中心となる問い

**「人間は、どこまで怠惰になっていいのか？」**

この問いを以下の4つの観点から扱う。

1. エンジニアリング：努力を削減することの価値
2. 認知科学：記憶や認知的負荷の外部化
3. ヘルスケア：生活の負担を減らすことと健康の関係
4. 倫理・社会実装：本人の意思、尊厳、プライバシー

## 1.3 この発表で主張したいこと

技術によって人間の負担を減らすことは、必ずしも人間の能力や尊厳を奪うことを意味しない。

しかし、技術が負担を取り除けば、それだけで人が幸せになるとも限らない。

重要なのは、単純に「何を自動化できるか」ではなく、**「何を人間自身が行うべきなのか、そしてそれを誰が決めるのか」**という問いである。

本発表では明確な正解を断言せず、2050年のヘルスケアに向けた議論の起点を提示する。

# 2. ターゲットと成果目標

## 2.1 想定聴衆

- 医師や医療従事者
- 医療・ヘルスケア関連企業
- 行政・患者団体関係者
- 学生・研究者
- テクノロジーに関心がある一般参加者

プログラミング経験がない人も理解できる内容にする。

## 2.2 LTの達成目標

発表後、聴衆が以下の3点を説明できる状態を目指す。

1. エンジニアの「怠惰」は、面倒を減らすための創意工夫を意味する。
2. E.D.I.T.Hは、人とのコミュニケーションを技術で支援しようとする試みである。
3. 人の負担を減らす技術には、利便性だけでなく、本人の意思や社会的影響を考える必要がある。

## 2.3 ブログの達成目標

- LTで省略した論点を体系的に整理する
- E.D.I.T.Hの技術的な背景や課題を説明する
- 自分自身の仮説に対する反論を検討する
- 関連研究や既存の技術を参照し、事実と意見を区別する

## Slide 2：怠惰はエンジニアの美徳である
**0:25〜1:05 / 40秒**

### 内容

Larry Wallによるエンジニアの三大美徳を紹介する。

- 怠惰（Laziness）
- 短気（Impatience）
- 傲慢（Hubris）

ここでの「怠惰」は、ただ何もしないことではない。

繰り返し発生する作業や面倒を減らすため、仕組みをつくろうとする態度である。

これを日常的な意味の「怠惰」と対比させる。

### 中心となる台詞

「エンジニアは怠惰なんです。面倒だから自動化する。でも、その結果として人間が何もしなくてよくなるとしたら、それは本当にいいことなんでしょうか？」

### LTでは削る内容

- Larry WallやPerlの歴史
- 三大美徳の詳細な解釈
- 自動化の具体例の列挙
- 生産性と幸福度の関係

これらはブログ第2章で展開する。

## Slide 3：記憶まで自動化できないだろうか？
**1:05〜2:25 / 80秒**

### 内容

自身が開発しているE.D.I.T.Hを紹介する。

**「覚えていなくても、名前がわかる。」**

E.D.I.T.Hは、顔認識などを利用し、相手の名前を思い出すことを補助するコミュニケーション支援プロジェクトである。

開発の背景にあるのは、情報を必ずしも人間の頭の中だけに保存する必要はないのではないか、という発想。

### 技術的な比喩

- 人間の脳：記憶と想起を行う仕組み
- 外部ストレージ：情報を保持する補助手段
- E.D.I.T.H：必要な場面で情報へのアクセスを補助する仕組み

ただし、これはコンピューターの仕組みを借りた比喩であり、人間の記憶がデータベースと同じ構造を持つという主張ではない。

### メッセージ

「人の名前をすべて覚えようとしなくても、必要なときに思い出す手段があれば、もう少し気楽に人と話せるかもしれない」

### LTでは削る内容

- E.D.I.T.Hの技術スタック
- 顔認識モデルの構成
- データベース構造
- システムアーキテクチャ
- 顔情報の登録・更新・削除フロー
- 他の記憶補助技術との比較
- 開発中に直面した課題の詳細

これらはブログ第3〜4章へ。

なお、実装済み機能と構想段階の機能は必ず区別する。

## Slide 4：その怠惰、本当に健康ですか？
**2:25〜3:35 / 70秒**

### 内容

ここで発表の方向性を反転させる。

技術で覚える負担を減らせたとして、それは必ずしも良いことだけではない。

具体的に以下の3つを提示する。

**1. 能力と依存**

記憶を外部に頼ることで、人間自身の能力や行動はどう変化するのか。

**2. 本人の意思**

技術によって支援されることを、本人が望んでいるとは限らない。

**3. プライバシー**

名前を覚えるために他人の顔情報を保存することは、本人の同意なしに正当化できない。

### 中心となる台詞

「覚えなくてよくなる。それは楽かもしれません。でも、便利になることと、健康になることって、同じなんでしょうか？」

### LTでは削る内容

- 認知的オフローディングの関連研究
- 記憶補助技術の実証研究
- デジタル依存の研究
- 個人情報保護法などの具体的な法制度
- 顔認識技術の公平性と誤認識
- 記録された情報の削除権限
- 本人の自律性とパターナリズム
- 利用できない人との格差

すべてブログ第4〜6章で検討する。

この部分は特に重要で、LTの時間不足を理由にブログから削らないこと。

# 4. 完全版ブログの構成

## 4.1 記事の位置付け

LTを文字起こしするのではなく、発表で扱った問題について深く考察する独立した記事にする。

読み手がイベントに参加していなくても理解できる構成とする。

**推奨文字数：8,000〜12,000字程度（上限は設けない）**

記事は技術ブログとしての読みやすさを維持しながら、思想的考察も扱う。

## 4.2 タイトル案

**怠惰は人を健康にするのか？ ― 記憶の外部化と2050年のヘルスケアを考える**

副題案：

「エンジニア三大美徳とE.D.I.T.Hから考える、人間が頑張らなくてもいい社会」

## 4.3 ブログ章構成

### 第0章：皆さん、怠惰ですかァ？

**目安：500〜800字**

- 2050 Project Fesに登壇した経緯
- LTの冒頭で「怠惰」を連呼した理由
- エンジニアとヘルスケアという、一見遠い2つの分野
- 本記事で検討する中心的な問い

導入は少しユーモラスにする。

ただし、記事全体をネタ調にはしない。

### 第1章：そもそも、ヘルスケアとは何か

**目安：800〜1,200字**

- 医療とヘルスケアの関係
- 治療だけでなく、予防、日常生活、社会参加なども健康に関係すること
- WHOの健康概念と、その解釈上の注意
- 健康と幸福、生活の質（QOL）の違い
- エンジニアが関与できる領域

医療の専門家ではない立場を明示する。

ispecからのスカウトを契機に医療DXに興味を持った経験は、この章で紹介する。

ただし、スカウトされたという事実以上の職務経験や医療業界での実績を主張しない。

### 第2章：エンジニアリングにおける怠惰とは何か

**目安：800〜1,200字**

- Larry Wallの三大美徳
- Lazinessの本来のニュアンス
- 日本語の「怠惰」との意味の違い
- 技術による自動化と抽象化
- 「面倒を減らすために面倒なことをする」という逆説
- 便利さと生産性の違い

取り上げる技術例：

- CI/CD
- Infrastructure as Code
- 型システムや自動テスト
- パスワードマネージャー
- 外部メモ・カレンダー

ここで本記事独自の問題設定へ移る。

**「人間の努力を削減することは、常に価値を生むのだろうか？」**

### 第3章：人間の記憶は、外部ストレージに置けるのか

**目安：1,200〜1,800字**

認知科学とエンジニアリングを接続する章。

取り扱う概念：

- 認知的オフローディング（Cognitive Offloading）
- 外部記憶と補助ツール
- 分散認知
- 拡張された心（Extended Mind）の議論
- 記憶の保存と想起の違い
- 知識を持つことと、情報へのアクセス方法を知ることの違い

重要なのは、これらの概念を同一視しないこと。

また「人間の脳＝ストレージ」「顔認識＝記憶」という単純化は、説明のための比喩として扱う。

記事では研究文献を確認し、それぞれの理論が実際に何を示しているのかを整理する。

### 第4章：E.D.I.T.Hという実験

**目安：1,200〜2,000字**

開発中のE.D.I.T.Hを具体例として紹介する。

扱う内容：

1. 開発の背景と課題意識
2. 「覚えていなくても、名前がわかる。」というコンセプト
3. 想定利用シーン
4. 現時点で実装済みの機能
5. 今後の構想
6. システムアーキテクチャ
7. データの取り扱いに関する課題
8. 開発を通じて気づいたこと

技術スタックや設計は、実際の実装を確認してから記述する。

可能であれば、個人情報を含まないデモ画像やアーキテクチャ図を掲載する。

特に、顔情報の取得や登録には本人の同意と適切な情報管理が必要であることを説明する。

本章の結末は、次の問題提起につなげる。

**「僕は人の名前を覚える負担を減らそうとしている。でも、それは本当にいいことなのだろうか？」**

### 第5章：怠惰によって、人間は何を失うのか

**目安：1,500〜2,000字**

記事で最も重要な考察部分。

以下の論点を分けて扱う。

**A. 技術への依存**

- 補助技術が使えないときの影響
- 利用者が自分で行えることとの関係
- 依存と支援の区別

**B. 記憶と人間関係**

- 名前を覚えることの社会的意味
- 人間関係における記憶の役割
- 情報を保持することと、相手を大切にすることの違い

**C. 本人の自律性**

- 利用者が支援を望んでいるか
- 技術を使わない自由
- 能力を補助することと、行動を一方的に代替すること

**D. プライバシー**

- 顔情報の取得と保存
- 同意
- データの削除
- 誤認識による影響
- 対象者以外への影響

**E. 健康への影響**

- 負担軽減とストレス
- 生活の質
- 技術の有効性をどう検証するか

「記憶を外部化すると認知能力が下がる」「外部化すればストレスが減る」といった主張は、根拠なしに断定しない。

### 第6章：エンジニアは何を決めてはいけないのか

**目安：1,000〜1,500字**

技術的に実現できることと、社会に導入すべきことは異なる。

論点：

- 技術者の価値観が仕様に反映されること
- 利用者中心設計
- アクセシビリティ
- 当事者参加型の設計
- 医療従事者、患者、エンジニアの協働
- 技術の効果・リスク・受容性を検証すること
- 技術を使わない選択肢の確保

E.D.I.T.Hを例に、技術を必要とする人へ届けるためには、コードを書くこと以外に何が必要かを考える。

イベントのセッションテーマである「新しい医療・発想を社会に届けるには？」との接続点とする。

### 第7章：2050年、人間はどこまで怠惰になれるか

**目安：1,000〜1,500字**

2050年の仮説的な社会像を提示する。

例えば、次のような技術が普及した未来を考える。

- 日常的な記憶補助
- 認知負荷を軽減するパーソナルAI
- 人間関係の維持を支援する技術
- 生活習慣や健康管理のサポート
- 利用者に合わせて変化するインターフェース

これらは未来予測として断定せず、思考実験として扱う。

そのうえで、次の観点から評価する。

- 人間の自由は増えるか
- 他者との関係はどう変わるか
- 利用者自身が選択できるか
- 特定の人を排除しないか
- 技術が使えなくても生活できるか

結論は「人間はすべてを技術に任せるべき」というものにはしない。

### 第8章：結論 ― 怠惰は人を健康にするのか？

**目安：600〜1,000字**

ここまでの考察をまとめる。

- 努力を減らすこと自体は悪ではない
- 努力を減らすこと自体が健康を保証するわけでもない
- 技術の価値は、その人の生活や意思との関係で決まる
- エンジニアの「怠惰」は、人を支えるための設計思想にもなり得る

最後はLTと同じ問いで締める。

**「人間は、どこまで怠惰になっていいのだろうか？」**

## 出典の扱い

- 学術的な主張には論文や公的機関の資料を付ける
- 実証されていない仮説には「仮説」と明記する
- 自身の体験は体験として記述する
- E.D.I.T.Hの設計思想と実証結果を区別する
- 関連性と因果関係を混同しない
- 反対意見も適切に取り上げる

# 7. スライドのデザイン要件

## 7.1 基本方針

**1スライド1メッセージ。**

5分間で読ませる文章量を最小限にする。

文字による説明よりも、言葉の対比と図解を優先する。

## 7.2 デザイン

- 画面比率：16:9
- スライド制作：Marpを想定
- 背景：基本は白または黒
- 強調色：1〜2色
- 本文：必要最低限
- 技術説明：単純な模式図
- 最終スライド：問いを大きく中央配置

## 7.3 スライドごとのビジュアル

| Slide | メインビジュアル |
|---|---|
| 1 | 「怠惰」の巨大な文字 |
| 2 | 怠惰・短気・傲慢の3ワード |
| 3 | 人間の脳と外部ストレージの模式図 |
| 4 | 利便性とリスクの対比 |
| 5 | 人間・AI・医療の関係図 |
| 6 | 「人間は、どこまで怠惰になっていいのか？」 |

アニメ作品のキャラクター画像は必須ではない。元ネタへの言及は冒頭の演出だけで十分。

# 8. クロストークへの接続

登壇後の議論を想定し、次の問いに対する回答を準備する。

### Q1. 記憶を補助することは、認知機能の低下を招くのでは？

補助技術が認知機能に与える影響は、利用方法や対象者によって異なる可能性がある。単純な因果関係として断定しない。

### Q2. E.D.I.T.Hを医療に使う予定なのか？

現段階ではコミュニケーション支援を目的とするプロジェクトであり、医療上の効果を実証したものではない。

医療への応用には、当事者や医療専門家との協働、実証、安全性・法制度の検討が必要となる。

### Q3. 顔認識技術におけるプライバシーは？

本人の同意やデータ管理は設計上の重要課題である。技術の便利さだけで正当化しない。

### Q4. なぜエンジニアがヘルスケアを語るのか？

医療の専門的知識を提供するのではなく、技術者が持つ「人の負担を仕組みで減らす」という考え方を、ヘルスケアの視点から問い直すため。

# 11. このプロジェクトの最重要原則

**「怠惰は正義である」という結論をつくるために、ヘルスケアを利用しない。**

反対に、技術への依存を無条件に悪だと決めつけることもしない。

エンジニアリングの美徳としての怠惰を出発点として、人間の健康・自由・尊厳をどう考えるべきなのかを探求する。

LTは問題を提示する場。

ブログは問題を検討する場。

両者は同じ問いから始まり、異なる深さで展開する。

**最終的に届けたいメッセージ：**

> 技術は、人間から努力を奪うためだけにあるのではない。
>
> 人間が、自分にとって大切なことに力を使えるようにするためにも存在する。
>
> だからこそ、何を技術に任せるかは、技術者だけで決めるべきではない。
>
> 2050年、人間はどこまで怠惰になっていいのだろうか？
