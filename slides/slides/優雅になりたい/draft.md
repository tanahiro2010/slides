# 優雅になりたい

## 概要

- 5分LT。クラシックを聴いて「所作まで優雅になりたい」と思ったところから始める
- Graceful Degradation を、想定外が起きても本質を残す設計思想として紹介する
- 技術用語を人の振る舞いに重ね、「優雅さとは余裕の設計である」と結ぶ
- 想定枚数は12枚。1枚1メッセージ、説明は口頭で補う

## LTスライドを作るに当たって

- 黒背景、金色の強調、明朝体の見出しで静かなクラシカルさを作る
- 章扉や情報量の多い表は使わない。コードは1枚だけ、比喩として置く
- 技術者には graceful degradation の意味が伝わり、非技術者には「余裕を残す」という言葉が残るようにする
- 参考: `references.md` のMDN / W3C / Microsoft資料

## 記事を書くに当たって

- スライドの各節を膨らませるが、クラシック音楽の効果を一般化しない
- Graceful degradation の定義、フォールバック、切り替え条件、利用者への通知を技術的に補足する
- `ElegantPerson.ts` は実装例ではなく、設計を考えるための擬似コードだと明記する
- 結論は冒頭に置く。「完璧に見せることではなく、壊れたときに本質と余裕を残すこと」

## 記事・スライド共通ドラフト

- タイトル「優雅になりたい。」
  - サブタイトル「人生にGraceful Degradationを実装する」
- 最近、クラシックを聴いている
  - 毎日聴いているうちに、音楽だけでなく所作まで優雅になりたくなった
  - ただし、ここではクラシック音楽の効果を証明しない
- 目指せ、優雅の化身
  - 紅茶をこぼしても顔色ひとつ変えない
  - 想定外の連絡にも「承知しました」と返す
  - 理想を並べるほど、現実の自分との差が面白くなる
- ところで、優雅とは？
  - ゆっくり動くことや、丁寧な言葉だけではない
  - 余裕、判断、配慮の3つに分けて考える
  - 優雅さを「結果」ではなく、崩れたときの振る舞いとして見る
- 人生、予想外が多すぎる
  - 予定変更、通信障害、寝坊、発表直前のトラブル
  - 完璧な正常系だけを想定すると、例外ひとつで全体が止まる
  - 問題は想定外が起きることではなく、起きた瞬間に選択肢がなくなること
- Graceful Degradationとは？
  - MDN: 最新環境で最善を作りつつ、古い環境でも本質的な機能を残す設計
  - Microsoft: 重要な経路を残すために非本質的な機能を縮退させる設計
  - 「全部できる」から「大事なことは続けられる」へ視点を変える
- 例外を正常系に
  - Unexpected Event → Panic → Crash は、余裕を使い切る流れ
  - Unexpected Event → Understand → Adapt → Respond は、選択肢を残す流れ
  - 重要なのは、障害を隠すことではなく、代替経路を先に決めておくこと
- ElegantPerson.ts
  - `composure`、`consideration`、`adaptability` を持つインターフェース
  - 失敗したら再試行するだけでなく、状況を説明して別の応答へ切り替える
  - コードは実行可能な実装ではなく、振る舞いを設計するための擬似コード
- 残念ながら、ビルドが通らない
  - `UnexpectedEvent` などは未定義で、現実の自分も未完成
  - 優雅さを実装したつもりでも、想定外の入力で落ちる
  - 未完成であることを隠さず、次の手を選べる状態を残す
- 優雅さ＝余裕の設計
  - 完璧に振る舞うことではない
  - 失敗時にも本質的な目的を守ること
  - 周囲に状況と次の選択肢を返すこと
- 余裕を、他人に分けられる人へ
  - 自分の復旧だけでなく、周囲の不安を増やさない
  - 「いま何が起きていて、次に何をするか」を伝える
  - それが人間におけるフォールバックである
- まとめ
  - 想定外はなくせない
  - 重要なものを決め、代替経路を用意できる
  - 優雅さとは、壊れないことではなく、壊れたあとも余裕を残すこと
- 締め
  - まずは紅茶の淹れ方を勉強する
  - Stay Graceful.
